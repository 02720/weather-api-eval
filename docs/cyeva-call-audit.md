# cyeva 调用审计（TASK-01）

>  reproduce：`python scripts/cyeva_audit.py --window-file tests/baseline/window.json`
> 环境：Python 3.12.8 / cyeva 0.2.3 / numpy 2.1.2；窗口 2026-08-01 ~ 2026-10-03（4 站 × 28 模型）

审计的目的不是"证明 cyeva 慢"（它慢是已知的），而是回答三个可量化的问题，
因为这三个问题的答案决定**该往哪儿使劲**：

1. 1,092 次调用里有多少次是重复计算？→ 能不能 memo 掉？
2. 有多少次是在门槛下算了也白算？→ 能不能把门槛提前？
3. 分级指标到底有没有被消费？→ 能不能不算？

---

## 1. 实测结果

| 项 | 数值 |
|---|---:|
| 被审计调用总数（precip + temp） | 2,632 |
| 指标调用总耗时 | 38.06 s |
| ├ `precip_metrics` | 1,092 次 / 33.07 s |
| └ `temp_metrics` | 1,540 次 / 4.99 s |
| **分级部分** | **896 次 / 26.65 s（占 70.0%）** |
| 分级展开的 cyeva 子调用 | 34,496（6 级 × 7 项，逐项重扫全序列） |

### 1.1 重复率：23.4%，但**可回收的时间几乎为零**

| | 调用 | 唯一键 | 重复率 | **memo 可回收** |
|---|---:|---:|---:|---:|
| `precip_metrics` | 1,092 | 836 | 23.4% | **0.02 s** |
| `temp_metrics` | 1,540 | 1,165 | 24.4% | **0.02 s** |

**这是本次审计最重要的结论，也是它与方案预估相反的地方**：方案 §4.5 措施二按
"减少 20–40% 调用次数"预估收益，但实测下来那些"重复"全部是**空桶**——
空输入哈希到同一个键，函数在构造 cyeva 对象之前就因 `n < min_sample` 提前返回了。
`precip_metrics` 的 1,092 次调用里有 303 次、 `temp_metrics` 有 414 次是空输入，
它们合计只花 0.06 s。

> **决策：不实现 memo 缓存。** 为 0.02 s 的收益引入一个以"输入内容哈希"为键的
> 缓存，代价是常驻内存（每个键一份样本副本）、失效规则（阈值/窗口一变就要清），
> 以及一条"为什么这份结果是从缓存来的"的新叙事。收益/风险比不成立。
> 这正是"先出审计报告再改代码"要防的事：凭估计动手会把力气花在 0.05% 上。

### 1.2 门槛后置：不成立

`precip_metrics` / `temp_metrics` **已经**在调用 cyeva 之前判定
`n < min_sample or n == 0 or n_eff < min_sample` 并提前返回，门槛本来就是前置的。
真正的浪费在别处——**`n_eff` 是在调用之前算的**，而它有 2,044 次调用、合计 9.7 s。
那里才是"为注定不入榜的格子付了成本"。这一点由 Phase 2 的列式化解决。

### 1.3 分级指标的消费面：**零消费**

- `report/_slim_report` 的字段白名单里没有 `graded`；
- `report.html.j2` 从未访问 `report.precip_hourly` / `precip_daily`（模板只用到
  `report.meta.*`、`report.leaderboards`、`report.coverage`）；
- 月度结论摘要 `data/metrics/{period}/summary.json` 只存 meta / coverage /
  scorecard / leaderboards，不存分级；
- 唯一引用 `graded` 的是两个测试（断言结构存在）。

也就是说：每轮 896 次调用、34,496 次子调用、26.65 s 算出来的分级指标，
**没有任何读者**。它不是"被展示的诊断信息"，而是"算了没人看的东西"。

## 2. 因此采取的措施

### 措施三（主收益）：分级指标走 numpy 快速路径

分级指标的数学只有两件事——一次区间比较、四个列联计数——而且**按级别可加**。
cyeva 对每个 `(级别, 指标)` 组合都把整条序列重新二值化一遍再用 `Counter` 数一遍，
于是同一份样本被扫了 77 遍。向量化实现把 77 次全序列扫描压成 2×级别数 次比较。

实现：`src/weather_eval/graded.py`
- 分级阈值**从 cyeva 自己的配置模块读**（`cyeva.config.levels.precip`），
  不存在第二份需要手工同步的阈值表；
- cyeva 保留为口径权威与对拍参照，**不修改、不移除**；
- 生产路径默认走 numpy，`eval.graded_backend: cyeva` 可切回权威路径。

**对拍前置条件已满足**：`scripts/parity_graded.py` 在真实数据上逐格比对
**711 个格子 × (5 或 6 级) × 7 项指标 = 约 4.6 万个数字，零不一致**；
`tests/test_graded_parity.py` 把这条不变量钉进 CI。

#### 复刻过程中抓到的口径陷阱（值得单独记一笔）

`calc_precip_*_indicators` 上的装饰器写作 `@source_round_digit(2)`，而该装饰器的
签名是 `source_round_digit(series_num=2, digit_num=1)`——那个 `2` 是**要舍入的前几个
位置参数**，不是小数位数。真正生效的位数是默认值 **1**。第一版按 2 位实现，对拍
立刻红了 200 处（`acc` 75.83 vs 79.46 这种量级的差），而肉眼看代码完全看不出来。
没有对拍脚本，这个错误会以"报告数字悄悄变了"的形式上线。

### 措施二：**按审计结果取消**（见 1.1）

不做 memo 缓存，理由已记在 1.1。

### 措施一：并行（TASK-02）

指标调用彼此独立、无共享状态，按 (模型, 天桶, 轨道) 分格子并行。实现见
`src/weather_eval/parallel.py`：
- 结果**按提交顺序**回收（worker=1 与 worker=4 输出逐位相同，
  `test_metrics_determinism_under_parallel` 锁定）；
- 任一 worker 失败整批退回串行，绝不返回"部分并行 + 部分串行"的混合结果；
- 批量 < 32 或小数据时走串行（测试与单源对照的行为与改造前完全一致）；
- `WEATHER_EVAL_METRIC_WORKERS=1` 可强制串行。

## 3. 收益（本机实测）

| 项 | Before | After |
|---|---:|---:|
| 指标调用总耗时 | 38.06 s | ≈ 6.5 s |
| 其中分级 | 26.65 s | ≈ 0.3 s |
| `build_report` 总计 | 103.5 s | 68.2 s（−34%） |

剩余的大头已不在 cyeva：`_resolution_boards` 18.7 s（含 bootstrap）、
`_compute_diagnostics` 15.9 s（见下）、`build_day_stat_tables` 10.7 s（已由 Phase 2
列式化继续压）、n_eff 9.7 s（同上）。

## 4. 附带发现：诊断层对冷层无感知（已修）

把诊断层改成复用内存快照时（TASK-04），发现它此前**根本读不到冷层数据**：

`report/diagnostics.iter_error_samples` 逐个文件 `_read_json` 后取
`snap.get("issue_iso")`，而月度 bundle 文件的**根节点**是容器
（`__bundle__` / `snapshots`），没有 `issue_iso` → 全部 `continue`。
于是诊断层只看见了当月的散装 `.json`，月度 bundle 里两个月的历史一概不可见。

| | 修复前 | 修复后 |
|---|---:|---:|
| 参与诊断的样本数 | 6,888 | **674,366** |
| `mean_rho` | 0.5815 | 0.6013 |
| `k_eff`（"27 家相当于几家独立信源"） | 1.68 | 1.62 |
| `k_families` | 1.0 | 7.0 |
| 指纹漂移告警源 | 3 个 | 4 个（多出 `cma_ndfs`、`fengqing_ai`） |

这不是性能问题，是**结论问题**：诊断层的招牌数字"27 家其实只相当于约 1.6 家
独立信源"此前是用 3 天的数据算出来的。修复的代价是耗时从 3.7 s 涨到 15.9 s——
用 12 秒换一个此前失真的结论，显然值得。
