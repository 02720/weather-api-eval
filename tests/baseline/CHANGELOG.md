# Golden Master 基线的变更记录

基线是"报告对外展示的数字"的冻结副本。它的价值来自**可比**，所以每一次重冻结
都必须写下"这次为什么重冻结、哪些字段变了、凭什么认为其它字段没变"。

不写这份记录，基线就会退化成一个每次红灯就重生成一遍的文件——那等于没有基线。

---

## 2026-10-04 · 第三次重冻结（n_eff 的 30/31 天悬崖：`effective_n` 换算成连续噪声下限）

重冻结原因：**口径变更**（`stats.effective_n` 的自相关校正）。总榜显示 UK Met Office
Global 10km"样本积累中"，但它的数据链路完全正常——每站日温度覆盖 37 天，与 JMA/GRAPES
逐日一致。差距出在 `effective_n`：旧实现有一个 `NEFF_MIN_SERIES = 30` 的**硬开关**，
每站序列 ≤30 天**完全不估自相关**、≥31 天**全额折减**。

### 缺陷是什么（第一性原理）

有效样本量的定义是"这份数据携带多少份独立信息"。同一条序列，**多攒一周数据不可能
让信息量变少**。硬开关让这个量在 30/31 天之间跳变：

| 窗口 | 每站日序列 | UKMO 日温度 n_eff | 总榜判定 |
|---|---|---|---|
| 9 月月报 | 30 天（走 guard，不折减） | **51** | 达标 |
| 跨月累计 | 37 天（走全额折减） | **18** | 掉出门槛 → "样本积累中" |

**加了 7 天数据反而更缺样本**，门槛判定翻转的根因是估计器"换挡"，不是数据不足——
这与本项目此前修掉的"每月 1 号样本清零"是同一族缺陷（日历节奏 vs 统计节奏）。
根源是窗口设计：跨月累计后日序列必然越过 31 天，guard 从"日轨道永不折减"整体翻到
"全额折减"档，而 `min_board_neff_daily = 20` 是在 9 月（每站恰好 30 天，guard 全程生效）
标定的，跨过档位后门槛判据已经失效。

### 处置

硬开关换成**连续噪声下限**：相关系数估计的标准误 ≈ 1/√n，只有超出 `z/√n`（z=1.64，
单侧 95%）的持久性才参与折减（`stats.NEFF_RHO_NOISE_Z`）。n→∞ 时下限趋 0，全额
校正照常生效；小序列的噪声 ρ̂ 按 0 处理，**保留**了原 guard 的本意（短序列不因噪声
凭空折损），但不再有断崖。回归测试 `test_stats_core.py::test_effective_n_no_cliff_when_series_grows`
用确定性序列钉住"样本变多 n_eff 不许变少"。

### 变了什么

对照实验把"口径变更"与"仓库漂移"分开：**用旧代码在同一份数据上重冻结一次**，与
HEAD 基线的差异即纯漂移（+40 份快照来自 10-04 15:28 那轮抓取，全部落在
`issue_anchors` / `snapshot_quality` / `integrity` / `diagnostics.fingerprint` /
`coverage.last_obs`，与本修复无关）；新代码与旧代码重冻结结果的差异才是本修复。
下表全部取自后者（同数据对照）。

| 字段 | 变化 | 性质 |
|---|---|---|
| `boards[*][*].qualified` | 2 处翻转：UKMO 在 `all` / `daily` 两张榜 `false → true` | **缺陷修复** |
| `boards[*][*].n_eff*` / `scorecard[*][*].n_eff` | 157+ 处（≥31 天的序列折减减轻：UKMO 日温度 19→37、ECMWF-IFS 27→46、JMA 32→50；≤30 天的序列首次受到阻尼后的温和折减：cma_ndfs 76→65、fengqing_ai 76→71、cma_public_v1 72→70） | **口径变更**（双向，见下） |
| `boards[*][*].score` | 80 处位移（最大 0.33，`cma_public_v1`）——总榜格子权重是 `√(格子 n_eff)`，n_eff 变即难度对齐权重变 | 传导结果 |
| `meta.difficulty_window.*` | 格子权重、逐桶难度、方差分解、等权对照分全部随之位移；`dropped_thin_cells` 总榜 10→2（小时榜 5→0、日榜 5→2）——原先被噪声误判为薄格的 8 个格子重新进设计 | 传导结果（门槛口径本身未动） |
| `meta.holm.family_actual` | `all`/`daily` 各 25→26（UKMO 达标后进入家族计数） | 传导结果 |
| `meta.diagnostics.corridor` / `rank_sensitivity` | `max_top10_changed` 1→0（等权对照下的名次对噪声更稳） | 传导结果 |
| **名次** | **0 处**（51 张榜 × 28 行） | — |
| `inputs.obs`（冻结输入指纹）/ `window` / `coverage.coverage_pct` | 未变 | — |
| `issue_anchors` / `snapshot_quality` / `integrity` / `diagnostics.fingerprint` / `coverage.last_obs` | 随仓库抓取轮次增长（+40 份快照），与本修复无关 | 仓库累计量 |

n_eff 的变化是**双向**的，且两个方向都是修正：≥31 天的序列此前按噪声全额折减
（UKMO 37 天、ρ₁≈0.45~0.63 却被折到 18）；≤30 天的序列此前一律按原始 n 记账、
完全不管自相关（cma_ndfs 每站 19 天、记 19×4=76）。新口径两侧都连续。

### 凭什么认为其它字段没变

窗口（`window.json`）与冻结输入指纹 `inputs.obs` 与上一版**逐位相同**——本轮
窗口内的配对、指标、bootstrap 输入一个字节没变，变的只有 `effective_n` 这一个
估计器及其传导（格子权重 → 难度对齐 → 分数/CI/名次）。51 张榜名次零差异、
最大分数位移 0.33 即是传导可控的证据。

## 2026-10-04 · 第二次重冻结（基线冻结在"活边"上：窗口必须已沉降）

重冻结原因：**上一版基线的窗口终点取在"最新观测整点"，也就是观测回改窗口的正
中央**。基线从冻结那一刻起输入就在移动，于是下一次抓取回改窗口内的一个整点，
对拍立刻红一片——而红的根因既不在代码里、也不在口径里。

### 变了什么

| 字段 | 变化 | 性质 |
|---|---|---|
| `window.end_dt` | `2026-10-03T23:00` → `2026-10-01T23:00`（已沉降终点） | **前提修正** |
| 全部 51 张榜单 / 评分卡 | 随窗口与观测回改而位移（1283 个展示字段、8 处名次互换） | 数据演化的必然结果 |
| `inputs.obs` | 新增（冻结输入的 SHA-256 指纹 + 各站小时数） | **新增凭证** |
| `perf_budget` | 149.7s → 131.5s、2798MB → 2715MB | 棘轮自动收紧（见下） |

### 凭什么认为代码没变（重冻结的前提）

**先证清白，再重冻结**：把 4 站的 `data/obs/*/2026-10.json` 还原成冻结当时的
内容（`git show a36d54dc:...`），在**当前代码**上重建报告——

* 51 张榜 × 28 行的全部展示字段与旧基线**逐位相同**（0 处差异），名次零差异；
* 还原后的唯一残留差异是 `diagnostics.fingerprint.checked_snapshots`
  （6689 → 6796），即下文第二次重冻结要处理的仓库累计量。

也就是说：**口径一位都没动**，位移 100% 来自观测回改。

### 缺陷是什么（第一性原理）

Golden Master 的全部价值来自"同输入必然同输出"。而本项目的输入并不都是不变
量——这是此前没人写下来的一层事实：

* **预报快照是不变量**：写一次就不再改（`save_forecast_snapshot` 幂等跳过 +
  Merkle 根可验）。
* **观测是活变量**：第三方源修正错报是常态。`obs/cma_data.py` 每轮回看
  `DEFAULT_LOOKBACK_HOURS = 26` 小时、其中最近 6 小时强制重抓，`save_obs`
  就地改值并把旧值挂进 `revisions`。于是任何比"最新观测 − 26h"更新的观测，
  都随时可能被下一轮改写。

第一版基线恰好把窗口终点放在最新观测上，等于把基线钉在活水的最前沿。实测的
代价：commit `03fd7ba0`（10-04 08:27 抓取）把 4 站 `2026-10-03T08:00` 的气温
回改了约 +1℃，于是——

* `acc2` 在第三位小数上位移（27/28 个模型，因为样本量上千，1 个整点的 1℃ 就是
  这个量级）；`n_eff` 变 1~2（自相关估计的小数进位）；
* 8 个模型的 `score` 跨越了展示精度的进位边界，于是**显示分打平的两家顺序
  翻转**——这就是 `第 19/20 名不一致` 看起来像"名次乱了"的真相：不是名次逻辑
  变了，是四舍五入的边界被推过去了。

### 处置（以及为什么不复发）

1. **窗口终点改为"已沉降"终点**：最新观测 − `SETTLE_HOURS`（48h = 26h 回看
   深度 + 两轮抓取周期 + 故障余量），再对齐到完整自然日 23:00。`window.json`
   记录 `settle_hours` / `settled` / `newest_obs_at_freeze`。
2. **`tests/test_baseline.py::test_window_is_settled`** 把"窗口已沉降"变成
   可失败的断言：对着**当下的数据**核验 `end + settle_hours ≤ 最新观测`。
   "在活边上冻结"当场失败，而不是等到某次回改之后以 1283 个字段的红灯失败。
3. **`inputs.obs` 输入指纹 + `test_frozen_inputs_unchanged`**：对拍变红时先看
   指纹——指纹变了是**数据变了**（查 `revisions`，重冻结并在此记一笔），指纹
   没变才是**口径变了**（代码事故）。两份哈希实现必然分叉，故指纹算法只有
   一份：`provenance.obs_input_digest`。
4. **已验证耐久**：在当前数据上再回改两个"下一轮够得着"的尾部整点
   （`2026-10-03T12:00` / `T20:00`，各 +1.3℃），8 个 golden 用例**全绿**——
   上一版基线正是在这里烂掉的。
5. **性能预算由棘轮自动收紧**（`_apply_ratchet`）：重冻结不得让预算变松，
   由代码守而不是靠人记得——换了更大的考题不等于变慢了。

### 顺带修掉的第二类假红灯：`fingerprint.checked_snapshots`

诊断层的 `fingerprint_drift` 读的是**全仓库**快照（含窗口之外、乃至窗口结束
之后才落盘的），所以 `checked_snapshots` 是仓库累计量：每轮抓取 +100 上下，
单调增长。逐位冻结它 = 每一次数据提交都让对拍变红，而报告一位没变。

处置：不逐位冻结，改为断言**只增不减**。这个下界本身就是警报器的一部分——
快照数**变小**正是"诊断层缩小了读取范围"（TASK-04 要防的那种失败）的直接
证据。窗口量（`source_correlation` / `station_rho`）仍逐位冻结。

## 2026-10-04 · 第一次重冻结（诊断层冷层修复 + 来源留痕）

重冻结原因：**修了一个诊断层的真 bug**，它的数字因此变了（见下）。其余字段经
逐位对拍确认**未变**——即"报告里印出来的每一个榜单数字"与修复前完全一致，
这也是本次重冻结被允许的前提。

### 变了什么

| 字段 | 变化 | 性质 |
|---|---|---|
| `meta.diagnostics` | 参与样本 6,888 → 674,366；`mean_rho` 0.5815 → 0.6013；`k_eff` 1.68 → 1.62；`k_families` 1.0 → 7.0；指纹漂移告警源 3 → 4 个 | **缺陷修复** |
| `meta.provenance` | 新增（`code_sha` / `lock_hash` / `bootstrap_seed` / `python` / 依赖版本） | **新增披露** |

### 诊断层的缺陷是什么

`report/diagnostics.iter_error_samples` 逐个文件读入后取 `snap["issue_iso"]`，
而**月度 bundle 文件的根节点是容器**（`__bundle__` / `snapshots`），没有
`issue_iso` → 被 `continue` 掉。于是诊断层只读到了当月的散装 `.json`，
两个月的历史（都在 bundle 里）一概不可见。

后果不是"少看了一点数据"，而是**招牌结论失真**：诊断层对外披露的
"27 家其实只相当于约 1.6 家独立信源"此前是用 3 天的数据算出来的。

修复方式：让诊断层复用 `build_report` 已在内存的全量快照（TASK-04）。副作用是
耗时 3.7 s → 15.9 s——用 12 秒换一个此前失真的结论。

### 凭什么认为其它字段没变

重冻结**之前**，先用上一版（未修复的）基线跑了一次完整对拍：
`test_report_matches_frozen_baseline` 绿，即 51 张榜 × 28 行的全部展示字段
（score / ci90 / champion_pct / sig_vs_top / qualified / n_eff / acc2 / rmse /
ts / ets / lead_days / n_days / track_gap）与修复前逐位相同，名次零差异。
也就是说，Phase 1 与 Phase 2 的全部改动（分级指标向量化、指标并行、n_eff 与
充分统计量表列式化）**没有改变任何对外数字**——这正是它们能被接受的前提。

### 顺带记录：两次"假红灯"

都发生在冻结/比对工具本身，而不是被优化的代码，值得留档以免重犯：

1. **基线序列化把浮点 round 到 6 位** → `scorecard[..].r` 基线 0.885263 vs
   实测 0.88526254…，差 4.6e-7 超过 1e-9 容差，对拍红了 20 行，而报告其实
   一位没变。教训：**基线不做任何舍入**，精度砍一刀之后"数字有没有变"这个问题
   就答不准了。
2. **cyeva 的 `@source_round_digit(2)`** 里的 `2` 是 `series_num`（要舍入几个
   位置参数）不是小数位数，真实位数是默认的 **1**。按 2 位实现分级指标后对拍
   红了 200 处。教训：**先写对拍脚本，再改实现**。
