# Golden Master 基线的变更记录

基线是"报告对外展示的数字"的冻结副本。它的价值来自**可比**，所以每一次重冻结
都必须写下"这次为什么重冻结、哪些字段变了、凭什么认为其它字段没变"。

不写这份记录，基线就会退化成一个每次红灯就重生成一遍的文件——那等于没有基线。

## 2026-10-25 · 第十次重冻结（第一性原理复核：综合分分层缩放 + 日轨 2:1 + 雨量去冗余 + 格子数门）

重冻结原因：**口径变更**（复核报告
`score-first-principles-audit-2026-10-24.md` 的 P0-1 / P1 / P3 / P4 落地）。
冻结窗口与第九版**逐位相同**（2026-08-01T00:00 ~ 2026-10-14T23:00，`--end` 显式指定），
所以差异只可能来自口径；观测输入指纹未变（`test_frozen_inputs_unchanged` 绿）。

### A. P0-1 入设计格子数门（`min_board_cells=4`，每轨）

n_eff 与降水事件门数的是"样本量"，而名次由行效应 α 决定——α 的精度取决于
**跨了多少个天桶**。新增：每条轨道至少 4 个格子入设计，总榜要求小时段与日段
各自达标（1 格小时 + 1 格日不再算"综合"）。未达标者与事件门同款处理：分数保留
为参考值、标"样本积累中"，不参与名次/冠军竞争，不发布 CI。

实测本窗口：既有 27 家入围源在三张榜上的围栏**零变化**（没有一家因这道门被
误杀；`cma_gowfs_v1` 本就因事件门未入围）。若某期出现"2 格源"（复核窗口的
`cma_gowfs_v1` 形态），它会被这道门直接拦在冠军竞争之外，而不再依赖窗外的
雨日门槛。

### B. P1 小时轨 : 日轨 = 2:1（`daily_track_weight=0.5`）

日轨的日最高/最低、日累计降水对绝大多数源是从同一份逐小时预报重新分箱得到的
（原生日产品只补了约 7.6% 的格子），两轨行分 Spearman 0.86。旧口径 1:1 把
"日极值"这一类信息的话语权凭空翻倍。新口径只缩放**总榜的日段拟合权重**
（门槛仍按未缩放权重判），单轨榜与 `all:Nd` 的合成也改用 1:0.5（=2:1）。

### C. P3 雨量精度去冗余

`amt_bias` 与 `amt_mae` 桶内原始相关实测 **+0.995（小时）/ +1.000（日）**（旧文档
"≈0.00"是硬错误），且 `amt_bias` 子分与降水分相关 −0.106/+0.132。`amt_bias` 退出
评分表，雨量精度族 22.5% 全部归 `amt_mae`；`amt_bias` 仍作为明细列发布。

### D. P4 综合分第二层缩放（`score_composite_gain=1.650`）

维度分 P99.5 已到 98，但两维平均后的综合分 P99.5 只有 **79.10**。新增第二层仿射
`g_c(s)=50+1.650·(s−50)`，只作用于综合分（维度分保持 1.851 的 gain 不变），
靶点 = 综合分 P99.5 → 98。**不是**把维度分 gain 改到综合分：后者会让温度维一半

CI 宽度按 1.65 放大（显示层）。

## 2026-10-24 · 第九次重冻结（模型 id 沿袭：DWD ICON Global 切换原生格点 + 新增两个 Open-Meteo 模型）

重冻结原因：**结构变更**（参赛者名单与一个系列的 id，不改任何评估口径）。冻结窗口
与第八版**逐位相同**（2026-08-01T00:00 ~ 2026-10-14T23:00，用 `--end` 显式指定）。

### 为什么这次必须重冻结

模型集合 29 → 31，三处变化一次性发生：

1. **沿袭切换**：`dwd_icon_global` → `dwd_icon_global_native`。Open-Meteo 公告
   2026-11-30 起 `dwd_icon_global` 系列改用原生格点，2026-10-24 提前切换；经逐站
   核对，两 id 的逐小时序列基本一致——这是**同一 ICON Global 产品的服务形态变更**，
   不是新模型。落地机制（`storage.FORECAST_MODEL_LINEAGE`）：历史存档以旧 id 落盘、
   **永不改写**（`payload_sha256` 锚定封存那一刻的字典），读取侧把旧 id 目录的快照
   **原样并入**接替 id 的系列，评估记录的归属映射到接替 id。于是基线窗口内
   `dwd_icon_global` 的全部样本原封不动地成为 `dwd_icon_global_native` 的样本——
   系列的赛道成绩完整延续，绝不重开零样本系列。
2. **接入** `dwd_aicon_global_native`（DWD AICON，AI 模式）与
   `meteofrance_arpege_world`（Météo-France ARPEGE World 0.25°，时效约 4.5 天）：
   冻结窗口内均无快照，照第六次重冻结的先例以**空行**入榜
   （`n=0`、`score=None`、`qualified=False`）。

榜单按"配置里的模型全集"出行：29 − 1（旧 id 折叠进接替 id）+ 2（新模型空行）=
**31 行**，`test_report_matches_frozen_baseline` 的行数断言必然红——这不是口径
漂移，是"参赛者名单变化"。

### 凭什么认为"其它字段没变"（重冻结前逐字段对拍）

用同一窗口重算一遍报告，与第八版基线**逐字段**比对：

* **沿袭的系列逐位继承**：每个榜上 `dwd_icon_global_native`（新）与第八版的
  `dwd_icon_global`（旧）**全部展示字段逐位相同**（score / temp_score /
  precip_score / ci90 / champion_pct / n / n_eff / acc2 / rmse / ets / ts /
  lead_days / n_days / track_gap…）——同一样本集、同一归属路径，只有 id 字符串
  换了名。这是"复用之前评测的数据"的机器可验形式；
* 其余 28 个既有模型的行：**0 处差异**，名次与分数逐位不变；
* 唯一新增：两个新模型的空行，不影响任何指标与名次；
* 其余差异全部归因于"六天里新归档的快照 + 观测推进 + 代码推进"：
  `integrity`（Merkle 根与快照份数——归并是读取侧行为，参与哈希的物理 dict
  集合与第八版完全一致）、`snapshot_quality` / `issue_anchors`（旧 id 的计数
  并入接替 id 名下，是沿袭的预期呈现）、
  `diagnostics.fingerprint.checked_snapshots`（9,566 → 10,7xx，仓库累计量）、
  `coverage.last_obs`（10-18 → 10-24）、`holm.m`（29 → 31，比对族随参赛者
  扩员）、`models` 列表、`provenance.code_sha`；另有
  `min_board_rain_events`/`min_board_rain_days` 首次出现在 meta——那是
  2026-10-23 已合入的 P8 第 3 条（降水事件证据门槛）的口径披露字段，第八版
  冻结时该提交尚未落库，与本轮结构变更无关。

结论：**没有任何既有评估指标发生变化**（沿袭系列的数字逐位延续），全部差异都能
归因于"评估集合变更 + 六天新归档数据 + 观测推进"。符合重冻结条件。

### A. P8 降水"最小存活权重"门槛（先于本次入账，此前未重冻结）

降水维 7 项里 5 项事件指标（`ets`/`pod`/`far`/`bias`/`grade_ets`，合计 0.775 名义
权重）需要真实降水事件才存在，2 项雨量指标（`amt_mae`/`amt_bias`）只要

冠军换人 5/51 张榜：`hourly:7d`（ukmo 伪造的 97.4 → `ecmwf_aifs025_single`）、

真失败格。

### B. P3 λ 全量复标（15 项）

上轮冻结值（2026-10-06）在冻结窗口上 **12/15 项实测子分 sd 跌破 8**
（最低 `amt_mae` 4.91）。重标后池化 sd 回到 8.00±0.01。标定窗口 = 冻结基线窗口。

⚠️ **标定目标本身的已知偏差（P9，本次未改）**：σ_k 统一标到 8 并不能兑现
"话语权 = 名义权重"——综合分是加权平均，贡献 ∝ w_k²·σ_k² 而非 w_k·σ_k，
故份额 ∝ w_k²。实测实际倍数 `ets` 0.87×、`acc1` 0.53×、`r` 0.14×、
`slope` 0.11×、`amt_bias` −0.12×，温度:降水 ≈ 42:58（名义 50:50）。
本轮把最离谱的 `amt_mae` 从 0.05× 提到 0.48×，但结构性偏差来自目标函数。
要真正修好需改标定目标为 σ_k ∝ 1/√w_k——那等于重设指标份额，属另一次口径
变更。见 `docs/score_review_proposal.md` §2 P9。

### C. P1 综合分上端留白（`score_index_gain` 2.66 → 1.851）

旧口径缩放前维度分 > 68.80 即 clip 到 100：实测 **71/1004 格（7.1%）**撞顶，
且 1d/2d 温度维成片（各 11/29 家钉在同一格）——温度维名义占综合分 50%，却在
对用户最重要的短时效里**零区分度**。根因是结构性：λ 只按 sd 标定、**没有上端
留白检查**，而 index_gain 假定缩放前水平在 50 附近，实测中位数却在 ~62。

新规则 **gain = (98−50)/(P99.5−50) = 1.851**（P99.5=75.93，2026-08-01~10-14），
把上端留白写进规则本身而非拍数。撞顶 **71 → 1 格**，且无同桶并列。
代价是整榜跨度收缩——这是自觉取舍："宁可跨度小，不要上端一整片撞线"。

## 2026-10-18 · 第七次重冻结（综合分"技能指数"缩放，修"区分度不足"）

重冻结原因：**口径变更**（评分体系的第一性原理审查，见 `config.eval.score_index_gain`
与 `stats.index_gain` 的注释）。冻结窗口与上一版**逐位相同**
（2026-08-01T00:00 ~ 2026-10-04T23:00，用 `--end` 显式指定以把"输入变了"从归因里
摘出去）——本次基线的全部差异都只能来自口径。

### 缺陷是什么（第一性原理）

读者读的"综合分"几乎全部挤在 ~10 分带里（总榜 27 家极差 10.53、小时榜 13.89、
日榜 9.47），**区分度不足**。根因不是斜率或权重，而是**聚合压缩**：

* 15 个子分各自被标定到"桶内跨源 sd = 8 分"（见 `score_slopes`）；
* 但综合分是这些子分**权重合计为 1 的加权平均**。互不完全相关的子分一平均，
  离散度就收缩到 ≈ 8·√(Σw²)·ρ修正 ≈ **2.8** 分；
* 实测印证：整榜 sd 2.76 ≈ 每张分时效榜的桶内跨源 sd 2.81——**压缩不在"跨时效桶
  求平均"那一步**（排除了中心极限式的跨桶稀释），而在"子分→综合分"这一步。

即**标定靶点打低了一层**：打在了子分上，而读者读的是综合分。

另一部分窄带是**诚实的、改不掉的**：跨源误差相关 ρ̄=0.61（29 家仅折合 1.6 家独立
信源），源间真实差异 sd 仅 ~2.5–3，单源 CI90 中位宽 7.2 ≈ 整榜极差的 70%——数据
本身能支撑的区分度就这么多，任何公式都无法把噪声变成区分度。

### 处置

在**子分加权平均之后**施加一次**冻结的仿射缩放** `g(s)=center+gain·(s−center)`
（`stats.index_gain`）：把综合分（以及温度分/降水分两个已显示维度分）的桶内跨源
sd 从 ≈3.0 标定回 **8 分**（与子分同名量纲）。`gain = 2.66 = 8 / 3.01` 反解自本基线，
冻结进 `config.eval.score_index_gain`（代码内缺省与之一致）。

* **不是按当期 μ/σ 自适应**：gain 是固定常数，若某期各家真一样，分数就一样——
  **不伪造区分度**。
* 点估计（`evaluate._weighted_score`）与 bootstrap（`stats._score_from_parts`）走
  **同一个全局**、同一把尺子，CI 中心不会与榜面数字分叉。
* 仿射且单调 ⇒ 名次与 Holm 显著性判定不变；gain=1.0 时 `index_gain` 走恒等快路，
  未装载配置的一切旧调用点**逐位不变**。

|---|---|---|---|---|---|
| 总榜 all | 10.53 → **26.13** | 2.81 → 7.02 | ecmwf_aifs025_single（不变） | 0.996 | 0 |
| 小时榜 hourly | 13.89 → **34.37** | 3.23 → 8.05 | ecmwf_aifs025_single（不变） | 0.996 | 0 |

### 凭什么认为"其它字段没变"

窗口与输入指纹逐位复用（`--end` 钉住），故差异只可能来自口径。51 张榜里
`score`/`temp_score`/`precip_score`/`ci90` 四类字段按上式整体重排；其余（n / n_eff /

## 2026-10-06 · 第五次重冻结（全指标入分：9 项 → 13 项）

重冻结原因：**口径变更**（全指标审计，见
[docs/metric_coverage.md](../../docs/metric_coverage.md)）。冻结窗口与上一版
**逐位相同**（2026-08-01T00:00 ~ 2026-10-01T23:00），观测输入指纹
`inputs.obs.sha256 = 3dd6b2f6…` 与上一版一致——差异只能来自口径。

### 缺陷是什么（第一性原理）

"温度分/降水分没有用上评测算出来的全部指标"——这话对，但"把每个指标都塞进加权
和"是最诱人也最站不住的修法：加权和的每一项都被当成一份独立证据，而多数指标
并不是。判据因此不是"相关性高不高"，而是三条可复算的问题：

* **Q1 恒等**——它是不是已有入分项的确定性函数？实测（936 温度格 / 356 降水格）：
  **χ² = RMSE²**（中位相对误差 2.4e−4，桶内斯皮尔曼 ρ **1.0000**，27/31 桶严格 =1）、
  **RSS = n×RMSE²**、**BIAS = POD/(1−FAR)**、**漏报率 = 100−POD**（精确），且给定 n
  的 2×2 列联表只有 3 个自由度而 {ETS,POD,FAR} 恰好撑满——用它们反解列联表重建
  acc/ts，中位相对误差 8.1e−4 / 1.3e−3。**所以 acc/ts/漏报率/POFD/χ²/RSS 不是
  "相关性高所以删"，是数学上不携带新信息。**
* **Q2 冗余**——acc1 对入分项的 1−R² = 0.123、mae = 0.036（相关 0.925 / 0.962），
  属"高度重叠但非同一量"；雨量 rmse/mae/mbe 的 1−R² = **0.93~0.99**，是评分轨上
  **唯一一块真新信息**。
* **Q3 可靠性**——雨量裸 mm 的桶内跨源 sd 逐小时 0.07、按天 1.35（差 20 倍），单一
  λ 标不出来；换成 Σ|f−o|/Σo 与 Σf/Σo 两个可加的相对口径后，小时/日的子分 sd 之比
  变成 **0.82 / 1.03**。

### 处置

1. **温度 5 项 → 7 项**：acc1 并入「命中轮廓」族、mae 并入「误差幅度」族，
   **族内等权**（族权重在成员间平分 = 族内先平均再按族权重入分，不新开槽位 →
   不重复计权）。权重表结构与所有下游消费者不变。
2. **降水 4 项 → 6 项**：新增「雨量量级」15% +「雨量总量偏差」10%，合计 25%——
   正是 2026-10-05 删掉 ts 空出的那个槽位；四项晴雨指标回到原始配比 35/15/15/10。
3. **雨量走可加的相对口径**（`amt_mae` / `amt_bias`）：可加性是**硬约束**——
   统计性质更好的 `1−MAE/mean|o−mean o|` 参考量不可加，按天分块 bootstrap 会
   静默换尺子，故弃用。同时把 `_RAIN_STATS` 从 4 列扩到 7 列（+Σo/Σf/Σ|f−o|），
   让 bootstrap 与点估计**同一把尺子**（`test_degenerate_bootstrap_reproduces_point_estimate` 守）。
4. **13 项统一重标定 λ**（标定期 2026-08-06~2026-10-05，60 天）：新增四项必须
   与既有九项同一标定期，否则"实际占比 ≈ 名义权重"的契约失效。逐项 λ 与核验
   见 [docs/score_slopes.md §八](../../docs/score_slopes.md)。
5. **拒收清单写进机器守卫**：`test_score_parts_contract` 锁死
   χ² / RSS / ts / acc / miss / farate 永不回到评分表。

### 缺陷是什么（第一性原理）

| acc2 | 25% | 38.7% | ×1.5 |
| bias | 10% | 27.3% | ×2.7 |

也就是说"README 说 RMSE 占四分之一"这句话是假的——真正决定名次的是**数据的
偶然分布**。叠加两个语义错误：BIAS 的线性式 `100−|BIAS−1|×100` 超报 2 倍即
0 分、欠报一半却得 50 分（不对称惩罚，且日轨 **56.9%** 的格子被压死在 0——

## 2026-10-04 · 第三次重冻结（n_eff 的 30/31 天悬崖：`effective_n` 换算成连续噪声下限）

重冻结原因：**口径变更**（`stats.effective_n` 的自相关校正）。总榜显示 UK Met Office
Global 10km"样本积累中"，但它的数据链路完全正常——每站日温度覆盖 37 天，与 JMA/GRAPES
逐日一致。差距出在 `effective_n`：旧实现有一个 `NEFF_MIN_SERIES = 30` 的**硬开关**，
每站序列 ≤30 天**完全不估自相关**、≥31 天**全额折减**。

### 缺陷是什么（第一性原理）

有效样本量的定义是"这份数据携带多少份独立信息"。同一条序列，**多攒一周数据不可能
让信息量变少**。硬开关让这个量在 30/31 天之间跳变：

| 窗口 | 每站日序列 | UKMO 日温度 n_eff | 总榜判定 |
|---|---|---|---|
| 9 月月报 | 30 天（走 guard，不折减） | **51** | 达标 |
| 跨月累计 | 37 天（走全额折减） | **18** | 掉出门槛 → "样本积累中" |

**加了 7 天数据反而更缺样本**，门槛判定翻转的根因是估计器"换挡"，不是数据不足——
这与本项目此前修掉的"每月 1 号样本清零"是同一族缺陷（日历节奏 vs 统计节奏）。
根源是窗口设计：跨月累计后日序列必然越过 31 天，guard 从"日轨道永不折减"整体翻到
"全额折减"档，而 `min_board_neff_daily = 20` 是在 9 月（每站恰好 30 天，guard 全程生效）
标定的，跨过档位后门槛判据已经失效。

### 处置

硬开关换成**连续噪声下限**：相关系数估计的标准误 ≈ 1/√n，只有超出 `z/√n`（z=1.64，
单侧 95%）的持久性才参与折减（`stats.NEFF_RHO_NOISE_Z`）。n→∞ 时下限趋 0，全额
校正照常生效；小序列的噪声 ρ̂ 按 0 处理，**保留**了原 guard 的本意（短序列不因噪声
凭空折损），但不再有断崖。回归测试 `test_stats_core.py::test_effective_n_no_cliff_when_series_grows`
用确定性序列钉住"样本变多 n_eff 不许变少"。

| `inputs.obs` | 新增（冻结输入的 SHA-256 指纹 + 各站小时数） | **新增凭证** |
| `perf_budget` | 149.7s → 131.5s、2798MB → 2715MB | 棘轮自动收紧（见下） |

### 凭什么认为代码没变（重冻结的前提）

**先证清白，再重冻结**：把 4 站的 `data/obs/*/2026-10.json` 还原成冻结当时的
内容（`git show a36d54dc:...`），在**当前代码**上重建报告——

* 51 张榜 × 28 行的全部展示字段与旧基线**逐位相同**（0 处差异），名次零差异；
* 还原后的唯一残留差异是 `diagnostics.fingerprint.checked_snapshots`
  （6689 → 6796），即下文第二次重冻结要处理的仓库累计量。

也就是说：**口径一位都没动**，位移 100% 来自观测回改。

### 缺陷是什么（第一性原理）

Golden Master 的全部价值来自"同输入必然同输出"。而本项目的输入并不都是不变
量——这是此前没人写下来的一层事实：

* **预报快照是不变量**：写一次就不再改（`save_forecast_snapshot` 幂等跳过 +
  Merkle 根可验）。
* **观测是活变量**：第三方源修正错报是常态。`obs/cma_data.py` 每轮回看
  `DEFAULT_LOOKBACK_HOURS = 26` 小时、其中最近 6 小时强制重抓，`save_obs`
  就地改值并把旧值挂进 `revisions`。于是任何比"最新观测 − 26h"更新的观测，
  都随时可能被下一轮改写。

第一版基线恰好把窗口终点放在最新观测上，等于把基线钉在活水的最前沿。实测的
代价：commit `03fd7ba0`（10-04 08:27 抓取）把 4 站 `2026-10-03T08:00` 的气温
回改了约 +1℃，于是——

* `acc2` 在第三位小数上位移（27/28 个模型，因为样本量上千，1 个整点的 1℃ 就是
  这个量级）；`n_eff` 变 1~2（自相关估计的小数进位）；
* 8 个模型的 `score` 跨越了展示精度的进位边界，于是**显示分打平的两家顺序
  翻转**——这就是 `第 19/20 名不一致` 看起来像"名次乱了"的真相：不是名次逻辑
  变了，是四舍五入的边界被推过去了。

### 处置（以及为什么不复发）

1. **窗口终点改为"已沉降"终点**：最新观测 − `SETTLE_HOURS`（48h = 26h 回看
   深度 + 两轮抓取周期 + 故障余量），再对齐到完整自然日 23:00。`window.json`
   记录 `settle_hours` / `settled` / `newest_obs_at_freeze`。
2. **`tests/test_baseline.py::test_window_is_settled`** 把"窗口已沉降"变成
   可失败的断言：对着**当下的数据**核验 `end + settle_hours ≤ 最新观测`。
   "在活边上冻结"当场失败，而不是等到某次回改之后以 1283 个字段的红灯失败。
3. **`inputs.obs` 输入指纹 + `test_frozen_inputs_unchanged`**：对拍变红时先看
   指纹——指纹变了是**数据变了**（查 `revisions`，重冻结并在此记一笔），指纹
   没变才是**口径变了**（代码事故）。两份哈希实现必然分叉，故指纹算法只有
   一份：`provenance.obs_input_digest`。
4. **已验证耐久**：在当前数据上再回改两个"下一轮够得着"的尾部整点
   （`2026-10-03T12:00` / `T20:00`，各 +1.3℃），8 个 golden 用例**全绿**——
   上一版基线正是在这里烂掉的。
5. **性能预算由棘轮自动收紧**（`_apply_ratchet`）：重冻结不得让预算变松，
   由代码守而不是靠人记得——换了更大的考题不等于变慢了。

### 顺带修掉的第二类假红灯：`fingerprint.checked_snapshots`

诊断层的 `fingerprint_drift` 读的是**全仓库**快照（含窗口之外、乃至窗口结束
之后才落盘的），所以 `checked_snapshots` 是仓库累计量：每轮抓取 +100 上下，
单调增长。逐位冻结它 = 每一次数据提交都让对拍变红，而报告一位没变。

处置：不逐位冻结，改为断言**只增不减**。这个下界本身就是警报器的一部分——
快照数**变小**正是"诊断层缩小了读取范围"（TASK-04 要防的那种失败）的直接
证据。窗口量（`source_correlation` / `station_rho`）仍逐位冻结。

## 2026-10-04 · 第一次重冻结（诊断层冷层修复 + 来源留痕）

重冻结原因：**修了一个诊断层的真 bug**，它的数字因此变了（见下）。其余字段经
逐位对拍确认**未变**——即"报告里印出来的每一个榜单数字"与修复前完全一致，
这也是本次重冻结被允许的前提。

### 变了什么

| 字段 | 变化 | 性质 |
|---|---|---|
| `meta.diagnostics` | 参与样本 6,888 → 674,366；`mean_rho` 0.5815 → 0.6013；`k_eff` 1.68 → 1.62；`k_families` 1.0 → 7.0；指纹漂移告警源 3 → 4 个 | **缺陷修复** |
| `meta.provenance` | 新增（`code_sha` / `lock_hash` / `bootstrap_seed` / `python` / 依赖版本） | **新增披露** |

### 诊断层的缺陷是什么

`report/diagnostics.iter_error_samples` 逐个文件读入后取 `snap["issue_iso"]`，
而**月度 bundle 文件的根节点是容器**（`__bundle__` / `snapshots`），没有
`issue_iso` → 被 `continue` 掉。于是诊断层只读到了当月的散装 `.json`，
两个月的历史（都在 bundle 里）一概不可见。

后果不是"少看了一点数据"，而是**招牌结论失真**：诊断层对外披露的
"27 家其实只相当于约 1.6 家独立信源"此前是用 3 天的数据算出来的。

修复方式：让诊断层复用 `build_report` 已在内存的全量快照（TASK-04）。副作用是
耗时 3.7 s → 15.9 s——用 12 秒换一个此前失真的结论。

### 凭什么认为其它字段没变

重冻结**之前**，先用上一版（未修复的）基线跑了一次完整对拍：
`test_report_matches_frozen_baseline` 绿，即 51 张榜 × 28 行的全部展示字段
（score / ci90 / champion_pct / sig_vs_top / qualified / n_eff / acc2 / rmse /
ts / ets / lead_days / n_days / track_gap）与修复前逐位相同，名次零差异。
也就是说，Phase 1 与 Phase 2 的全部改动（分级指标向量化、指标并行、n_eff 与
充分统计量表列式化）**没有改变任何对外数字**——这正是它们能被接受的前提。

### 顺带记录：两次"假红灯"

都发生在冻结/比对工具本身，而不是被优化的代码，值得留档以免重犯：

1. **基线序列化把浮点 round 到 6 位** → `scorecard[..].r` 基线 0.885263 vs
   实测 0.88526254…，差 4.6e-7 超过 1e-9 容差，对拍红了 20 行，而报告其实
   一位没变。教训：**基线不做任何舍入**，精度砍一刀之后"数字有没有变"这个问题
   就答不准了。
2. **cyeva 的 `@source_round_digit(2)`** 里的 `2` 是 `series_num`（要舍入几个
   位置参数）不是小数位数，真实位数是默认的 **1**。按 2 位实现分级指标后对拍
   红了 200 处。教训：**先写对拍脚本，再改实现**。
