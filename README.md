# 天气预报 API 准确度评估系统

把 12 个来源、28 个预报模型的逐小时预报**先存档、后对账**：预报必须在实况出现之前封存，事后才与气象站观测逐点比对。每天自动跑三次，生成一份可在线浏览的排行榜 `reports/index.html`。

> **只想看结论？** 打开报告 → 顶部冠军卡一句话（附"读榜须知"）→ 往下看 **§01 预报源总榜**。总榜已经把各家"能预报多少天"的差异扣掉，报 3 天的源和报 15 天的源在同一个榜上是公平的。

## 1. 它到底在做什么

```
   抓取预报（起报快照，原样封存）          抓取观测（事后到达）
            │                                    │
            └──────────► 按整点时间戳配对 ‹───────┘
                              │
                    按"提前 N 天"分档 → 算指标 → 加权成 0~100 分
                              │
                    ┌─────────┴─────────┐
                 总榜（难度对齐）    提前 N 天分榜（同难度对照）
```

**三条不可越界的原则**（整个项目的地基）：

1. **预报必须在实况之前封存**，落盘后永不回改。任何"事后取数"都会污染评估。
2. **缺测绝不伪装成数值**。缺测就是缺测，绝不折算成 0.0——否则"预报无雨"会和"没数据"混为一谈。
3. **不确定的事要显式披露**：置信区间、样本量、覆盖天数、验证日数都摆在榜上，让读者自己判断结论有多厚。

**接入了谁**（`config/stations.yaml` 可增删）：

| 类别 | 源 |
|---|---|
| 国际主流数值模式 | ECMWF IFS / AIFS、GFS、AI-GFS、HGEFS、ICON、GRAPES、GEM、GSM、UKMO（经 Open-Meteo） |
| 国内商业 API | 彩云天气、和风天气、AccuWeather、MSN（底层中国天气网）、中科星图 |
| 国内 AI / 科研模式 | 中科天机（5 个变体）、伏羲中期 / 伏羲确定性、风乌 GHR、CMA-NDFS、风清 AI |
| 官方公众接口 | 中国气象局公众气象服务网（weather.cma.cn） |

观测来自[环境气象数据服务平台](http://eia-data.com)，4 个广西/海南气象站（梧州、博白、平南、万宁）的逐小时气温与降水。

观测是本项目**唯一的真值来源**，因此它不能只有一条链路。抓取走**多源编排**（`obs/chain.py`）：主源 eia-data 健康时完全不碰备用源；主源失败，或**抓通了但数据陈旧/窗口截断**时，自动降级到[中国气象数据网](https://data.cma.cn/dataGis/static/gridgis/#/pcindex)的站点实况接口按 WMO 站号补齐。合并结果的来源构成逐轮写进日志留痕（详见 [第 9 节](#9-按源口径与已知坑位)与 [`obs/chain.py`](src/weather_eval/obs/chain.py)）。

## 2. 报告怎么读

报告页面自上而下（2026-09 重构后只回答一个问题：**谁家预报最准？**）：
**冠军卡（含"读榜须知"硬数字）→ §01 预报源总榜（服务端渲染，无 JS 也能读；下方三个折叠区：口径注记 / 评分构成 / 难度对齐与稳健性 + 起报锚点公示）→ §02 得分衰减曲线（小时/日口径 × 综合/温度/降水）→ §03 温度/降水指标图 → §04 每日热力图 → §05 预报 vs 实况 → §06 分站对比 → 机制与可审计性 / 名词词典（折叠）→ 月度归档**。

冠军卡下方那一行"📏 读榜须知"是**必读**：它直接给出样本期天数、重采样次数、90% 区间中位宽、与第一名统计上并列的源数、权重扰动下的冠军归属。名次的解读边界写在结论旁边，而不是藏在附录里。

榜单的「综合分」列是一条**温度计**：蓝色柱 = 分数在 0~100 刻度上的位置，两端金色须线 = 90% 置信区间——须线重叠的两家，先后在统计上还说不清。「得分走势」列是综合分随提前天数（1~16 天，小时口径）的衰减迷你线，灰色虚线为全体中位。

### 排行榜的三个维度：分辨率 × 时效

预报有两个互不等价的可预报对象，本系统把它们**分开评、再合成**（2026-09 双轨道重构）：

| 榜单 | 回答什么 | 口径 |
|---|---|---|
| **总榜**（默认） | "综合来说谁家最准"（跨两种分辨率） | 小时榜与日榜放进同一个加法模型 |
| **⏱️ 小时榜** | "某日几点报得准不准" | 逐小时温度 + 该小时 ≥1mm 是否在下雨 |
| **📅 日榜** | "这一天的极值/总量报得准不准" | 日最高/最低温度（两量各评再平均）+ 日累计 ≥1mm |
| **`all:Nd`** 综合天榜 | "提前第 N 天这天，综合谁最准" | 该天小时榜与日榜的分数各半合成（两轨缺一即缺） |
| **`hourly:Nd` / `daily:Nd`** 分时效榜 | "同分辨率、提前第 N 天，谁最准" | 同难度直接对照，最保守的视角 |

两条轨道为什么必须分开：小时尺度天然更难（要报准雨落在哪一小时），日极值天然更平滑（取一天的最值），两榜同样"少 1 分"不是同一件事——直接平均等于假设两个不同口径的分数可以相减。

总榜的正确合成方式是把"列"从"天桶"换成 **(天桶 × 分辨率)** 的笛卡尔积：第 5 天的小时预报与第 5 天的日预报是**两档不同的难度**，各自的列效应分别估计，两个口径的尺度差被各自的档位截距吸收。总榜逐行披露 `track_gap`（小时榜分 − 日榜分）：绝对值大 = 这家在两种分辨率上强弱不一致，单一总榜数字对它代表性有限。

**入围门槛跟着 n_eff 的计数单位走**（四个门各配各的阈值，总榜要求全过）：

| 维度 | n_eff 数的是什么 | 门槛 |
|---|---|---|
| 逐小时温度 | 独立小时误差 | `min_board_neff`（30） |
| 逐小时晴雨 | 独立小时判定 | `min_board_neff`（30） |
| 日最高/最低 | 独立自然日 | `min_board_neff_daily`（20） |
| 日累计降水 | 独立雨日 | `min_board_neff_rain`（20） |

小时榜的降水阈值是 **1mm/h** 而不是业务"有降水"的 0.1mm：在 0.1mm 口径下数值模式普遍每小时产生微量降水（drizzle bias），实测预报基率是实况的 2.7 倍、ETS 全部挤在无区分度的窄带里，分数实际在给"谁更少毛毛雨"排序；提到 1mm/h 后预报/实况基率趋于一致（BIAS 中位数 2.69 → 1.26），分数才开始测技巧。标定扫描见 `scripts/calibrate_hourly_threshold.py`（日累计口径的同款标定见 `scripts/calibrate_daily_threshold.py`）。

分时效榜是**同难度直接对照**（同一分辨率、同一档提前量，各家比同一批天气），永远是最保守、最不需要假设的视角。

### 总榜上几个关键列

| 列 | 说明 |
|---|---|
| **难度对齐分** | 名次依据。把每档（提前天数 × 分辨率）有多难先算出来并统一扣掉后的综合分 |
| 小时榜 / 日榜 / 两榜差 | 同一份数据只看一种分辨率的对齐分，及两者之差（`track_gap`）——源 × 分辨率交互的显式披露 |
| 90% 置信区间 | 这个分数的波动范围；区间重叠的两家，名次先后更多是抽样运气 |
| 覆盖时效 / 覆盖桶数 | 这家实际被验证到提前第几天、占了几档（两家分数接近时，能报更久的那家更难得） |
| 起报轮次 / 验证日数 | 这份分数有多厚的底子：23 轮起报、18 个验证日 ≠ 1 轮起报、3 个验证日 |
| n_eff（有效样本量） | 已扣除时间自相关与**跨站相关**后的独立信息量，四个维度各自披露（单位不同，门槛也不同） |
| ⚠️ 口径存疑 | 该源命中"起报锚点≈抓取时刻 / 残缺快照 / 城市吸附 / 整数温度"中的任一条，悬停可看具体理由 |

**常见误读**：

- ❌ "这家排第 12，肯定不行" —— 先看置信区间与 † 标记（† = 与第一名的差距经多重比较校正后**不显著**）。
- ❌ "这家覆盖 15 天、那家只有 5 天，分数却差不多，所以前者更强" —— 总榜已扣掉难度差；长度差异只体现在"覆盖"列，属于额外信息而非加分。
- ❌ "TS 只有 0.3，这家的雨报得很差" —— 降水比温度难报得多，TS 到 0.3~0.5 已属正常水平。

### 曲线图的用法

- **选几家都不限**：用「🎯 对比源」里的「全选」一次看全部 28 家。

## 3. 快速开始

```bash
python3.12 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt -r requirements-dev.txt
pip install --no-deps cyeva==0.2.3   # 必须单独装，见下方"依赖坑"

export PYTHONPATH="$PWD/src"         # src 布局且未打包，需手动加导入路径

python -m weather_eval fetch-obs                       # 抓观测
python -m weather_eval fetch-forecast                  # 抓 Open-Meteo 快照
python -m weather_eval fetch-forecast --source tianji   # 其他源同理，凭据先设环境变量
python -m weather_eval report                          # 生成 reports/index.html
```

抓取是**幂等**的（按 站点 × 模型 × 起报时刻 去重），重复运行不产生冗余数据；单次失败不丢数据，下次运行会自动补回近 24h 的观测窗口。

### 命令一览

| 命令 | 作用 |
|---|---|
| `fetch-obs [--source auto\|eia_data\|cma_data]` | 抓取各站近 24h 观测并归档。默认 `auto` = 多源编排：主源可用时不惊动备用源，主源失败/陈旧/截断时自动降级补位 |
| `fetch-forecast [--source X]` | 抓取预报起报快照并归档（默认 Open-Meteo，其余源见 [第 9 节](#9-按源口径与已知坑位)） |
| `report` | 用"本月 1 号至今"的累计数据覆盖更新主报告 `reports/index.html` |
| `monthly [--month YYYY-MM] [--force]` | 把某月冻结为月度归档 `reports/monthly/YYYY-MM.html`（默认上一自然月）。已存在的归档拒绝重写，`--force` 才允许重建；同时把该月**结论**固化为 `data/metrics/YYYY-MM/summary.json`（体积治理的前提），随后重建主报告 |
| `compact [--grace-days 2] [--retain-months 13] [--apply] [--force]` | **体积治理主线**：把已结束的自然月的逐份快照合并成一份 `{YYYY-MM}.json.gz`（实测 21× 压缩、文件数降两个数量级），并把超过保留期的冷层出仓。默认 dry-run、幂等；出仓前必须已固化该月结论摘要，否则拒绝删除 |
| `archive [--days 60] [--apply]` | 逐份快照 gzip 归档（`.json` → `.json.gz`，压缩比约 8~12×）。**已被 `compact` 取代**（月度合并的收益是它的 2.8 倍且文件数少两个数量级），保留用于旧流程兼容 |
| `health [--stale-hours 30]` | 写源健康度看板 `reports/health.html`（各源最近成功时刻、残缺率、起报锚点构成）；有源超过阈值未成功抓取时以非零退出，供 CI 自动开 Issue |
| `footprint [--warn-mb 400] [--fail-mb 900]` | 仓库体量看门狗：报告 `data/` 冷热分层占用与 `.git` 体积（含历史）；超硬阈值非零退出，CI 据此自动开 Issue |
| `verify [--period YYYY-MM]` | 重算全部快照的 Merkle 根并与 `data/manifest/` 清单比对；不一致即非零退出（存档被事后改写的机器可检证据） |
| `all` | `fetch-obs` + `fetch-forecast` + `report`，CI 的主步骤 |

### 依赖坑（照做即可）

- Python 必须是 **3.12**（cyeva 0.2.3 不支持 3.13）。
- cyeva 的元数据把 `pint` 误钉为 0.24.3，而 0.24.3 在 Python 3.12+ 上无法导入。因此**必须**用 `--no-deps` 单独装 cyeva，由 `requirements.txt` 提供可用的 `pint==0.24.4` 及其真实依赖。升级 pint 前先确认 cyeva 仍可导入。

### 数据体积怎么持续可控

起报快照是**只增不减的证据流**（实测约 170 份/天、单份中位 18.9 KB、约 2.8 MB/天；一年 ≈ 6 万文件 / 1 GB 原始 JSON）。本项目的两条地基要求它必须留在 git 里（先封存后用、事后可核验），而 git 会永久保存每一个版本——两者相加就是一个单调增长、最终让"每天自动跑三次"变成不可能的曲线。治理分三层：

**第一层：让每一轮新增的字节尽量少（布局）。** 单份快照的 **59.8% 是同一条时间轴**（`hourly_time` 在 27 个模型间几乎完全相同），逐文件 gzip 完全吃不到这份跨快照冗余。`compact` 把**已结束的自然月**合并成一份 `{YYYY-MM}.json.gz`：

| 布局 | 单站 27 模型 17.0 MB 原始 JSON | 压缩比 | 文件数 |
|---|---|---|---|
| 散装 `.json` | 17.0 MB | 1× | 4,119 份 |
| 逐文件 gzip（旧 `archive`） | 1.95 MB | 8.7× | 4,119 份 |
| **月度 bundle（`compact`）** | **0.70 MB** | **24.2×** | **27 份/月** |

在真实仓库上实测：8 月共 92 个包，**12.76 MB → 0.61 MB（21.1×）**，删除 792 个散装文件，耗时 4.6 秒。

**第二层：让不再需要的数据离开工作区（保留期）。** 分层口径是自然月（因此幂等、可重放、结果与运行时刻无关）：

| 层 | 范围 | 形态 | 支撑什么 |
|---|---|---|---|
| 热层 | 当月（+2 天宽限） | 逐份 `.json` | 主报告、月度冻结、`verify` |
| 冷层 | 已结束的自然月 | 一份 `{YYYY-MM}.json.gz`（**冻结，永不重写**） | 长期可复核的原始证据 |
| 出仓 | 超过 13 个月 | 删除 | 结论已由冻结的月度报告与该月指标摘要固化 |

**先固化、后删除**是这里的核心纪律，而且是机械执行的：出仓前会检查 `data/metrics/{period}/summary.json` 是否存在（由 `monthly` 在月初写下，含总榜与分时效榜），不存在就**拒绝删除**并报红。所以 `data/metrics/` 不再被 gitignore——"体积变小"永远不能以"结论不可复核"为代价。

**第三层：让失控可见（看门狗）。** 前两层按月生效，而一次意外写入（源疯狂重试、分片爆炸、误提交大文件）能在一天内把仓库推高几个数量级。`footprint` 在每轮 CI 里报告冷热分层与 `.git` 体积，超过 900 MB 即让作业变红并自动开 Issue。CI 里 `compact --apply` 每轮都跑（幂等，无可冻结时零操作）。

**归档不改变任何指标口径**，这不是口头承诺而是被钉死的不变量：回归测试与 CI 的 `verify` 步骤共同要求"压缩前后 **Merkle 根**与**总榜逐位**相同"（`tests/test_compact.py::test_bundle_preserves_snapshot_set_and_merkle_root`）。读取侧（`list_forecast_snapshots`）对两种布局一视同仁地展开成同一批快照。

> **历史体积的人工回收**（需人工决策，不做自动化）。上面三层管的是"工作区"与"以后的新增"；但 `.git` 里**已经存在**的旧版本不会被删除动作回收——`compact` 删掉 8 月的 792 个散装文件后，它们仍留在 git 历史里。要把这部分也收回来，需要在一次人工操作中重写历史（`git filter-repo` 剥掉旧路径，或在数据分支上重建单个提交后 force-push）。这一步会改写提交哈希，因此**刻意不做成自动化**：
>
> 1. 先确认冻结包与月度摘要都已提交（回收的前提是"信息已固化"，判据同上）；
> 2. 用 `git filter-repo --path data/ --invert-paths`（或按需只剥 `data/forecasts/**/*.json`）重写历史；
> 3. force-push 后，所有协作者需要重新 clone（旧 clone 无法 pull）；
> 4. 回收后 Merkle 清单仍然有效——`verify` 校验的是**当前工作区**的哈希聚合，与提交历史无关。
>
> 判断"要不要做"：跑一次 `python -m weather_eval footprint`，若 `.git` 体积远大于 `data/` 分层占用之和，差值就是历史里的旧版本，值得回收。

## 4. 自动运行（GitHub Actions）

1. 推送仓库（需包含 `data/` 与 `reports/`），在 **Settings → Pages** 把部署源选为 **GitHub Actions**。
2. 工作流 `.github/workflows/eval.yml` 每天**北京时 06:00 / 13:00 / 20:00** 运行：抓观测和各源预报 → 覆盖更新主报告 → **体积治理（`compact --apply`）** → 提交数据 → 部署 Pages。提交与部署带 `if: always()`——即使某一步失败，当轮已落盘的快照也会入库（**预报快照错过起报就无法追补**），失败信号由作业状态保留。
3. 每月 1 号额外把上一自然月冻结为月度归档（也可 `workflow_dispatch` 手动指定月份；已存在的归档自动跳过，绝不重写），并固化该月结论摘要。
4. 各商业源的凭据配置为同名 Secret（`CAIYUN_TOKEN` 等）；**未配置的源自动跳过**，已配置但抓取失败只标注该步骤、不阻断主流程。
5. 观测抓取（`all` 步骤内的 `fetch-obs`）走多源编排：主源可用时不惊动备用源，降级时逐轮留痕——不需要任何额外 Secret。
6. 每轮附带**仓库体量看门狗**（`footprint`）：`.git` 超过 900 MB 即让作业变红并自动开 Issue，把"某天起 clone 变慢"这种事后才被发现的静默劣化变成当场可见的信号。

## 5. 评估方法

### 样本与时效

- 预报与观测按**北京时整点**精确配对。观测 `rain@t` 覆盖 (t−1h, t]，各预报源的入库口径见 [第 9 节](#9-按源口径与已知坑位)。
- 每个（起报, 有效时刻）组合是一条独立样本，按实际时效（lead = 有效时刻 − 起报时刻）归入 1–16 的「提前 N 天」天桶。**短时效样本天然更多**，时效曲线正是要反映"越临近越准"。
- 另做**按天评估**：北京时自然日的日最高/最低气温、日降水量；观测与预报任一侧当日非缺测小时数不足 `daily_min_hours`（默认 20）时该天不入样。
- **样本下限**：`n < min_sample`（默认 5）视为样本不足，不出结论。

### 有效样本量 n_eff

逐小时气温误差强自相关（实测 lag-1 ρ ≈ 0.64~0.91），名义样本量把同一信息重复计数（实测高估 4.6~20.5 倍）。总榜入围门槛与样本判定均以 `n_eff = n·(1−ρ₁)/(1+ρ₁)` 为准（按站独立估计、同一有效时刻只取最新一版起报）。

**还要扣掉跨站相关**（2026-09 修正）。时间维度的自相关校正只解决了一半问题：它默认"各站相互独立"，但相邻站的误差由同一批天气系统驱动（实测同一源温度误差的跨站 ρ̄ ≈ 0.229）。k 个各含 n_eff 信息的站，合起来的信息量只有独立情形的 `1/(1+(k−1)ρ̄)`——4 站时约 0.59，也就是说**按站求和会把 n_eff 高估约 1.7 倍**，总榜入围门槛随之形同虚设。现在 `n_eff_from_station_series` 按公共时刻估计两两相关 ρ̄ 后除以该因子；历史结论的 n_eff 因此普遍下降，这是修正而不是数据变差。

顺带修掉一处数值缺陷：ρ 的估计曾写成 `np.cov(a,b)/√(var(a)·var(b))`，而 `np.cov` 用 `n−1` 归一、`ndarray.var()` 用 `n` 归一，会把 ρ 系统性放大 `n/(n−1)` 倍——对完全相关的序列会算出 **1.0208** 这种数学上不可能的相关系数，并在小样本上频繁误触 `RHO_CLAMP` 截断。现在统一走 `np.corrcoef`。

### 相关系数与回归斜率按站内合并

跨站池化的 r 混入"复现站间气候差异"这一容易得多的任务（实测与站内口径差最多 0.084，约合 1.3 个综合分）。r 在各站内部计算后按 Fisher-z 变换加权合并，斜率按样本量加权合并；池化值保留在 `r_pooled` / `slope_pooled` 并列披露。

### 评分体系

综合得分 =（温度分 + 降水分）/ 2，每个子分由互不重复维度的代表性指标加权而成，统一换算到 0~100；某项缺数据时按**剩余权重**归一（缺数据 ≠ 差数据，不让单一缺项把整行踢出局）。

- **温度分**：±2°C 准确率 25% ＋ RMSE 换算分 25% ＋ 相关系数 r 15% ＋ ±1°C 准确率 10% ＋ MAE 换算分 10% ＋ \|MBE\| 偏差换算分 10% ＋ 回归斜率换算分 5%。
- **降水分**：ETS 35%（首位）＋ TS 25% ＋ POD 15% ＋ 100−FAR 15% ＋ \|BIAS−1\| 换算分 10%。

**两个关键取舍**：

- **降水入分的轨道是按天 24h 累计、日雨量 ≥1mm 记"有效降水日"**（`rain_daily_threshold_mm`，业务惯用口径）。原因：逐小时 ≥0.1mm 口径下数值模式普遍每小时产生微量降水（drizzle bias），实测各源超报 2.7~15.3 倍、全模式 ETS ≤ 0.054（满分 1.0），分数被压在无区分度的窄带里；24h 累计让毛毛雨在求和中自然抵消，1mm/日阈值下 ETS 上限恢复到 0.25（阈值扫描见 `scripts/calibrate_daily_threshold.py`）。逐小时晴雨指标保留为诊断视图，不进综合分。
- **晴雨准确率 acc 不入分**：它主要由气候基率决定（无雨日 70%+，"全答无雨"即可拿高分），不是技巧；ETS 本身已做过基率校正。POD 权重（15%）低于 FAR+BIAS（25%），评分不奖励"多报占便宜"。

权重表是 `evaluate.py` 的 `TEMP_SCORE_PARTS` / `PRECIP_SCORE_PARTS`——评分、页面"评分构成"表与本文档三处的单一数据源。RSS、χ²、雨量 RMSE/MAE/MBE 等指标照算但不入分（理由见代码注释）。

### 逐日预报补位（`daily_source_fallback`，默认开）

多数 API 的**逐日预报比逐小时预报覆盖得更远**（逐小时常止于 5~10 天，逐日可到 15 天）。逐小时一断供，按天评估就跟着断在第一段时效上——即便该源明明还有日预报。快照因此支持一个可选的逐日预报块：

```json
"daily_time": ["2026-09-06", "2026-09-07"],
"daily": { "模型名": {"temp_max": [...], "temp_min": [...], "precipitation": [...]} }
```

按天轨道走**双轨**：该日逐小时覆盖达标 → 用逐小时聚合（与历史存档同一口径，旧数字不变）；覆盖不足 → 回退源自带的日产品，该条样本记 `temp_src`/`rain_src="daily"` 并分开计数，报告"明细表②"按"补位数/总数"披露。

**评测范围 = 日偏移 1..16 天**（`daily_max_offset_days`）：部分源的日产品可铺到 30~90 天，但两周以上的日预报没有业务意义，超出范围的部分**不做评测**；入库时写路径会把日产品的超范围部分截除（`snapshot_meta.truncate_daily_block`，实测某源 90 天日产品截到 17 天，省 82% 该块体积），不让永不评测的数据永久占据仓库。

边界（不可越界）：

1. **绝不由日产品反推逐小时序列**——那是凭空造出日内变化；逐小时指标、分时效榜与总榜永不掺入日预报。
2. **观测侧门槛不放松**：实况当天不足 `daily_min_hours` 照样不入样；日产品缺测就是缺测，绝不折算 0.0。
3. **口径差异只披露不消除**：日产品的日界与"逐小时求和"相差约 1 小时边界，同一日偏移桶内可能两种来源混存。日界必须是北京时自然日——中国天气网"白天/夜间"那类日界不得照抄，接入前必须在 provider docstring 里核实留档。

各源是否提供日产品（2026-09-05 逐源实测核实，证据见各 provider docstring）：

| 源 | 逐日块 | 说明 |
|---|---|---|
| Open-Meteo | ✅ 全三要素 | 同一次请求顺带取回，零额外调用；逐小时本就覆盖满 16 天，补位保持休眠 |
| 和风天气 | ✅ 全三要素 | 旧版 v7 逐日 3/7/10/15/30d 逐档回退。**真实时效增益 +5~20 天**。v7 官方 2027-02-01 停服 |
| AccuWeather | ✅ 全三要素 | 官方逐日 15/10/5/1day 逐档回退；降水 = Day/Night 两个半日 TotalLiquid 之和 |
| 中科星图 | ✅ 仅温度 | **降水拒绝接入**：pre_day/pre_night 呈恒 5.0 的量级码形态，与自家逐小时矛盾 90 倍 |
| 彩云天气 | ✅ 仅温度 | **降水拒绝接入**：daily.precipitation 只有日内统计量（max/min/avg/probability），无累计字段 |
| 中科天机 / 风乌 / 伏羲 / MSN / EW4ALL / 公众网 | ❌ | 无"北京时自然日"口径的逐日极值产品，或日界不可对齐（证据见各 docstring） |

## 6. 总榜为什么这么算：难度对齐

**问题**：预报难度随时效单调上升，而各家能预报的天数从 3 天到 16 天不等。于是——

- 直接把各家"自己覆盖到的那几档"平均起来，**只报近几天的源白拿简单档的分**：实测全窗口分与覆盖桶数 r = −0.54，每多覆盖一档平均扣 0.74 分。
- 只取所有源共同覆盖的交集来比，26 家同榜时**窗口只剩 4 天**——九成样本被扔掉。

**做法**：把（源 × 提前 N 天）这张表看成

```
S(m, b) = μ + 技巧_m + 难度_b + 噪声
```

用**全部**格子联合估计行效应（各家水平）与列效应（各档难度）——双向加法模型，交替最小二乘（实现：`stats.two_way_adjust`）。总榜的分数就是"若各家都被验证在同一批难度上，各值多少分"。数据一格不扔，也不要求各家覆盖一致。

几个实现上的硬约束：

- **只有两维齐备的桶进矩阵**（温度与降水都有分）。缺一维的桶不是综合分，是"温度分换个名字"。
- **每个格子至少 3 家同台**（`MIN_MODELS_PER_BUCKET`）。只有 1~2 家的档，"难度"与那家的"水平"分不开，留着等于发白卷。家数不足时阈值自动下调到 2；只剩 1 家时无从比较，退回各家桶平均分。
- **二分图不连通时只保留最大分量**——分量之间的水平差异不可识别，把它们并进一张榜等于宣称无从得知的结论。
- **加法假设要留一分清醒**：若某家在短时效特别强、长时效特别弱（源 × 时效的交互），对齐后的单一数字表达不了，请改看「提前 N 天」分榜。**交互项到底占多少方差**由 `stats.variance_decomposition` 量化并进报告披露（源间/时效/残差三份额），跨桶名次一致性由 `stats.bucket_rank_stability` 给出。
- **不确定性同口径**：置信区间、冠军频率、权重敏感性都走同一张劈分设计、同一个归总函数（`stats.difficulty_adjusted`），保证区间属于榜上那个数字。退化检验（bootstrap 权重全置 1）必须逐格复现点估计——这条不变量由回归测试钉死。

### 格子样本量必须进权重（2026-09 修正）

上面那套劈分原先**等权**拟合——每个（源 × 提前 N 天）格子权重恒为 1。而本项目的格子样本量跨**三个数量级**：温度侧中位数从第 1 档的 2,360 到长尾档的 788，降水侧从 92 到 36，个别格子只有个位数。等权等于宣称"5 条降水样本算出来的 0.0 分"与"92 条样本算出来的 34 分"同样可信——**名次于是变成噪声排序的产物**，长尾档的列效应还会等量地打进每一行。

现在的做法：

- **按格子信息量加权**：`w = √(min(温度 n_eff, 降水 n_eff))`。取两维较小者，因为综合分承诺两维各半，一格能不能说话取决于更薄的那一维；取平方根是为了不让最厚的格子垄断整个拟合。
- **格子最低样本量门槛**（`min_cell_neff`，默认 15）：低于门槛的格子**直接剔出设计**，而不是靠 `min_sample=5` 放行。门槛与权重的量纲必须一致（换算到权重单位后再比），否则门槛会要么形同虚设、要么一次清空全部格子——两种失败都表现为"设计被降级"，不报错。门槛因数据规模不足而被放宽时会打 `gate_relaxed` 标记并进披露。
- **长尾档单独成榜**（`board_min_col_frac`，默认 0.5）：同台家数不足"最热闹那一档的一半"的天桶不进主设计，其"难度"由极少数薄格子估出，会把噪声等量打进所有源的行分。被剔除的档在报告里以**参考值**单独列出，不参与总榜名次。
- **列效应可收缩**（`board_ridge`，默认 0 关闭）：家数少的档，其难度可向平均值收缩（经验贝叶斯式），而不是靠 7 个薄格子给出一个污染全榜的极端值。
- **等权对照并列披露**：名次对加权方式的敏感度（Spearman 与前十换了几家）随报告给出——榜单不能只给加权后的名次就完事。

`board_cell_weighting: "neff" | "equal"` 可切回旧口径做对照；回归测试锁定"等权 + 不收缩时与旧实现逐位相同"。

### 温度与降水必须同窗（2026-09 修正）

天桶原先用 `(lead−1)//24+1` 分温度桶，即"起报后的第几个**滚动 24 小时**"；而降水侧用的是"有效日 − 起报日"的**自然日**。两者不是同一个时间窗：实测同一个「提前 1 天」里，Open-Meteo 的温度分 96% 来自**起报当天**、风清的 72.5% 来自起报次日，而降水分对所有源都严格是"起报次日全天"。两维日历构成完全不同，却被平均成同一个数字。

现在温度也用**日历日偏移**：`提前 N 天` 对温度与降水都指"起报日之后第 N 个自然日"。起报当天的剩余小时不进任何天桶（以 `bucket=0` 的哨兵保留在记录里，只供固定时效窗的明细指标），因此**温度与降水的样本集合逐格同窗**。

### 起报当日不进天桶，因此不计入"这一行的证据量"

总榜行的 `n` / `覆盖时效` / `验证日数` / `n_eff` 只统计**进天桶**的样本（`bucket ≥ 1`）。全 lead 的配对数另存 `n_all_leads` 供明细口径核对——否则一行会用一批没参与打分的样本虚报自己的证据量。

### 派生列与综合分逐格同集（2026-09 修正）

榜单里"难度对齐综合分"与"难度对齐 ±2°C 准确率"原先各用**各自的非空掩膜**拟合：某源某桶因降水缺测而没有综合分，它的 `acc2` 却仍参与该行的难度估计——于是页面上的两列来自两批不同的格子，"所有数字列走同一张设计"只是 row/col 掩码层面的半真话。现在综合分的格子掩膜是唯一设计（`cell_valid` 随披露落盘），所有派生列强制同集，缺格即 —。

报告里"⏱️ 难度对齐是怎么做的"与"🔬 这份名次有多结实？"两节会列出**每一档的难度值、参与家数、格子权重分布、交互方差占比、跨桶名次一致性、加权敏感度**，读者可以自己核对。

### 其他不确定性信息

- **90% 置信区间**：按天分块 bootstrap（`bootstrap_runs` 默认 500 次，固定种子可复现）。块长由日尺度误差的去相关时间决定（`bootstrap_block_days`，0 = 自动，实测 ρ ≈ 0.46 → 2~3 天），并受"块数 ≥ 6"约束——块长 1 天只捕获日内相关，实测会把区间算窄 40%~90%。
- **Holm–Bonferroni 多重比较校正**：26 家同榜、每家都与第一名比一次，α=0.1 下至少一次假阳性的概率约 93%。名字带 **†** = 与第一名差距校正后仍不显著。
- **权重敏感性**：把各项权重各扰动 ±40% 重复 500 次，看冠军在几家之间轮换。多家轮换说明头名之争并未一锤定音。
- **入围门槛（qualified）**：`n_eff ≥ min_board_neff`（默认 30）**且**降水维 `n_eff_rain ≥ min_board_neff_rain`（默认 20）**且**温度/降水两维都有分。未达标的源列"样本积累中"，不参与冠军竞争。

### 快照契约：把"先封存后验证"从自律变成可验证（2026-09 修正）

项目最重要的一条地基是"预报必须在实况之前封存"。此前它**完全依赖 provider 作者的自觉**：快照里没有任何抓取时间戳（`grep fetched_at` 零命中），当某个 provider 把"抓取时刻"或"页面缓存更新时间"填进 `issue_iso` 时，不但没有机器检查能发现，事后也没有任何存档证据能追溯。

现在每份快照落盘时都由**唯一的写入口**（`storage.save_forecast_snapshot`）盖上契约元数据，provider 漏写也不可能漏字段：

| 字段 | 含义 | 为什么必须有 |
|---|---|---|
| `fetched_at_bj` / `fetched_at_utc` | 抓取时刻（北京时 / UTC） | "这份快照到底是什么时候抓的"从此永久可考 |
| `payload_sha256` | 快照内容哈希（排除自引用字段后计算） | 事后改写可被机器发现 |
| `issue_source` + `issue_raw` + `issue_source_declared` | 起报锚点语义 + 原始字段 + 是否真的由 provider 声明 | 见下 |
| `complete` / `missing_shards` | 完整性标记与缺失分片清单 | 残缺快照不再伪装成完整外壳 |
| `actual_hours` / `resolution_hours` | 实际点数 / 原生分辨率 | "3 小时产品被平铺成逐小时"不能与原生逐小时混为一谈 |
| `precip_unit` / `precip_accum_window_hours` | 降水单位与累计窗口 | 累计量口径必须声明而非靠 docstring 约定 |

**起报锚点语义**是其中最要紧的一项。`issue_iso` 在本项目里其实有**五种互不等价的物理语义**（真实模式轮次 / 时间轴首点 / 数据更新时间 / 请求时刻下取整 / 未知），却在同一张排行榜上比较。当锚点实质接近抓取时刻时，该源声明时效会系统性地长于实际时效——等于被评在更容易的样本上。契约要求每源显式声明（各 provider 的声明见 [第 9 节](#9-按源口径与已知坑位) 与报告页的"各源的起报时刻到底是什么"），评估层据此分层披露，并对命中以下**正面证据**的源打上 **⚠️ 口径存疑** 标记：

1. provider 显式声明的锚点属于"≈抓取时刻"或"未知"；
2. 存在残缺快照（分片未取全）；
3. 存在空间吸附（`location_distance_km`）——样本代表城市而非站点；
4. 温度被量化（`quantized_temp`）——整数摄氏度自带 ±0.5°C 量化误差。

历史存档（2026-09 之前）没有声明字段，一律记 `unknown` 但**不判争议**，只以"未声明份数"披露可审计性覆盖率——标记一旦对所有人都亮，就等于没有标记。

**哈希链与 Merkle 根**：每轮运行把全部快照的哈希聚合成一个根，写入 `data/manifest/YYYY-MM.json` 与报告页。任何人克隆仓库后运行 `python -m weather_eval verify` 即可重算比对，任何对存档的事后改写都会让 CI 变红。这是把"工程自律"升级为"可验证"的最小实现。

**残缺快照默认排除**（`require_complete_snapshots`，默认开）：接口只返回部分分片的快照会被标成 `complete=false` 并**不参与评估**——残缺样本与完整样本同权进榜，会把"这家少抓了一半数据"混进"这家报得准不准"。排除份数在报告里逐源披露。历史存档无该字段，按完整处理，因此**不改变任何既有结论**。

### 源健康度：消灭"静默死亡"

CI 里 9 个抓取步骤全部 `continue-on-error: true`，失败只写日志。一个源连续 30 轮抓不到数据，唯一信号是"作业状态偶尔变黄"——而对于"预报快照错过即无法追补"的项目，这等于**用静默换取样本期的空洞**。

`reports/health.html`（由 `health` 命令生成，与主报告同批刷新）逐源给出：最近成功时刻（`fetched_at` 与 `issue` 两个口径）、快照数、覆盖站点数、残缺数、缺抓取时刻数、起报锚点语义构成。判定规则：**曾经有数据、但最新快照超过 `--stale-hours`（默认 30 小时 = 连续 4 轮失败）未更新**即标红并使命令非零退出，CI 据此自动开 Issue；**从未接入的可选源不算故障**（缺 Secret 是正常状态，当成故障会让告警迅速失去意义）。

### 其他工程修正

- **CI 不再静默吞掉变基冲突**：`git pull --rebase --autostash ... || true` 会让 rebase 失败（冲突、autostash 弹出失败）静默通过，随后照常提交——可能把当轮数据提交到一棵陈旧的、与远端分叉的树上。现在失败即 abort 回退到变基前状态（当轮产物一个不丢）并以非零退出，同时自动开 Issue。
- **归档写入原子化**：旧实现直接写目标 `.gz` 再删源文件，中断会留下半截 `.gz` 并被 git 收进仓库，变成一份永久损坏的"档案"。现在先写临时文件再原子改名。
- **观测回改写进 `revisions` 数组**：第三方观测源会修正早期错报，静默覆盖会让"当时的实况"不可复原——而实况是评估里唯一的真值来源。现在每次改动的时间戳与新旧值都留痕（日志照打，但证据不再丢失）。
- **provider 级缓存按 (模型, 站点) 建键**：EW4ALL 的"哪一轮要素齐全"被当成模式级事实供其余 3 站沿用（探测站恰好落在偏旧/偏新轮次时，4 站的 `issue_iso` 会一起错位且不报错）；中科天机的 `_failed_models` 把单站失败记成模型级故障（一次单站抖动被放大成整轮缺失）。两处都已按站点建键。
- **超时统一 + 单源总时间预算**：各源原先分别用 `(10,60)/(10,30)/60/30` 四套超时且没有任何总预算——一个慢源可以用"每次请求都在超时边缘再退避重试"吃掉整个作业的时间。现在超时统一到 `http.DEFAULT_TIMEOUT`，`TimeBudget` 让重试与分片请求共享单源总预算，耗尽即明确失败（可见的失败优于"看起来正常、实际只抓了一半"的慢速成功）。
- **负降水按缺测处理**：旧实现只 WARNING 就照常入库，契约漂移的迹象会直接变成降水评分里的负样本。超过浮点容差即置缺测（既不伪装成 0，也不污染指标）。

## 8. 接入新的站点 / 模型 / 预报源

- **新增站点**：`config/stations.yaml` 的 `stations` 下加一项（`id`/`name`/`lat`/`lon`/`obs_url`）。若要接 `cma_public`（预报）或让站点走 `cma_data`（观测备用源），另加 `cma_id`（该站 WMO 站号）；未配时这两个源的抓取都会**响亮失败**，绝不猜站号。
- **新增观测源**：实现 `obs/base.py` 的 `ObsSource` 接口（返回 `{"time", "temp", "rain", ...}` 列表，最新在前），然后**三处同步登记**：`obs/chain.py` 的 `OBS_SOURCE_PRIORITY`（顺序即权威顺序）、`__main__.py` 的 `_build_obs_sources`、以及 `config/stations.yaml` 的 `obs_sources`。优先级语义（高优先级源已给出的时刻不被低优先级覆盖）由编排层实现，新源无需自己处理覆盖问题。
- **新增模型**：Open-Meteo 模型直接加进 `models`；中科天机模型需先在 `forecast/tianji.py` 的 `MODEL_SPECS` 登记。
- **新增预报源**：实现 `forecast/base.py` 的 `ForecastProvider` 接口，在 `__main__.py` 的 `SOURCE_SPECS` 登记一个 `--source`（模型集合与提供方工厂在同一处登记，勿分两张表），评估逻辑无需改动。**报告层三张登记表必须同步**：`report/render.py` 的 `MODEL_LABELS`（中文名）/ `MODEL_COLORS`（配色）/ `MODEL_FAMILIES`（分组）——由守卫测试 `test_all_models_registered_in_report_layer` 机器校验，漏登任何一张表 CI 直接红。

几个通用要求：

- HTTP 重试/熔断直接用 `forecast/http.py` 的 `request_with_retries`（4xx 立即熔断、5xx/429 与网络错误退避重试、末次不 sleep），不要再手写循环。
- **时间分辨率粗于逐小时时，重采样只能用 `forecast/resample.py` 的两个函数**（连续量线性插值 / 累计量平铺均摊），并在 provider docstring 里论证窗口方向与口径假设。
- 各源的降水入库口径变更，应在对应 provider 内实现并留档（`config/stations.yaml` 不再提供全局偏移配置——它是按源而非按站生效的）。

参考实现：`caiyun.py` / `qweather.py` / `geovis.py` / `accuweather.py` / `msn.py` 覆盖官方 API、网页抓取、档位回退、SSR 状态抽取；`ew4all.py` 覆盖"一次抓取返回多个各自独立起报的快照"；`cma_public.py` 覆盖"公开 JSON 接口 + 固定粗网格 + 缺测哨兵值"。

### 各源逐个说明

**Open-Meteo**：不回显底层模式的真实起报轮次，快照锚点是北京时当日 00:00（与真实 init 相差 −8~+12h 且随抓取时刻漂移），每天仅 1 份快照。同一天桶内其预报难度与样本新鲜度与其他源略有差异。免费档约 1 万次/天，无需 Key，但批量回溯请控制频率。

**彩云天气**：返回点数与 User-Agent 强相关，代码中固定的 UA **勿改**（改了会被静默截断至约 48 小时）；逐小时时间戳锚定在请求时刻，已下取整到整点配对。

**AccuWeather**：服务条款限制将数据用于"评级、排名、评审"类用途，与本项目公开排行榜的定位存在**潜在冲突**，是否接入请自行评估。定位是"最近城市吸附"而非格点（实测 4 站吸附距离 1.8~7.0 km），报告"口径注记"会展示实际吸附距离。

**MSN 天气（底层中国天气网）**：抓的是页面**服务端渲染内嵌的状态块**（`redux-data`），改版即可能失效。一次只渲染一天逐小时，一份快照需按 `day=1..10` 抓 10 次请求/站（本仓库请求量最大的源）；`day>10` 会被服务端静默回退为滚动窗口。起报时刻是推断值（取 `lastUpdated` 下取整整点）。**温度为整数摄氏度**，自带约 ±0.5°C 量化误差，RMSE/±1°C 准确率等指标相对小数温度的源存在系统性劣势。实现以"一份快照绝不跨版本"为不变量，绝不静默混合两个数据版本。

**EW4ALL（CMA-NDFS / 风清 AI 模式）**：抓的是模式预报页背后的公开接口（前端 bundle 逆向），无官方契约。

- **失效形态是"返回空 `data`"而非报错**——mode/要素名写错、轮次未出数、接口改版都表现为空列表。实现以"空数据绝不建快照"为不变量（空快照会被幂等键永久锁死），且起报轮次必须**温度与降水同时有数据**才采纳。
- **接口原生时间是 UTC**，入库前统一 +8h。证据：(a) 观测与模式日变化互相关最佳平移 +7~+8h、r=0.946（+0h 时 r 为负）；(b) 按 UTC 解释时序列末点恰为起报 +240h/+360h 的整数时效；(c) 入库后 lead 1~8h 温度 RMSE = 1.23°C，而错 8 小时应对应 4~6°C。这类偏差不报错、只会静默污染全部样本，故写死在 docstring 里备复核。
- **起报锚点是"平台标注轮次"**：平台在标注轮次**之前**即可返回该轮数据，且一轮内分要素先后出数（先温度、后降水），故最新一轮常在降水出数前被跳过（下次运行可正常捕获）。
- **CMA-NDFS 的降水是两级产品**：1 小时产品只覆盖起报后约 72h，之后退化为 3h 累计摊薄。两者总量高度一致（合并总量比 0.98），但逐窗口有 30% 的点偏差 >0.35mm——"日总量接近、日内分布有出入"。每份快照的 `precip_1h_until` 留档交接点、`expansion` 留档展开方式，可机器核对。
- **温度分辨率**：CMA-NDFS 逐小时到 +72h、其后逐 3 小时；风清全程逐 6 小时。插值不产生新极值，因此按天评估的日极值恒等于该模式**采样时刻序列**的极值。风清采样落在北京时 02/08/14/20 时，夹在采样点之间的日极值取不到，表现为**日最低系统性偏暖、日最高系统性偏低**——这是 6 小时分辨率的精度上限，非接入缺陷。
- 不做格点回显：响应不含吸附格点坐标，`grid_lat/lon` 记请求坐标；底层网格 5km（CMA-NDFS）/ 约 25km（风清）。

**中国气象局公众气象服务网（weather.cma.cn）**：公开 JSON 接口 `/api/hourly/{WMO 站号}`，游客态可用。

- **User-Agent 有反爬名单**：`python-requests/2.34.2` 与 `curl/8.5.0` 被 403 拒，浏览器 UA、空 UA 与仓库统一 UA 均通过。403 属确定性失败（立即熔断）。若日后仓库 UA 被误伤，改 `HEADERS` 这一处即可。
- **失效形态是"HTTP 200 + 空 `data`"**：站号写错也返回 `{"msg":"success","code":0,"data":""}`。实现以"空数据绝不建快照"为不变量。
- **分辨率是 3 小时**（接口名 `api/hourly` 是接口名而非分辨率），时刻恒落在北京时 02/05/08/11/14/17/20/23。**日极值的采样偏差小于 6 小时分辨率的源**——采样点恰好贴近真实日最低（05~06 时）与日最高（15~16 时），这是该源的隐藏优点。
- **缺测哨兵 `999.9`**：长时效点上降水回填 `999.9`（同现 `weather=999`、`text="9999"`），**而同一行的温度仍是有效值**。按"非物理值即缺测"处理（≥999 或负值）并计数留档。表现为该源长时效降水样本偏少，**不是模式少报**。
- **起报锚点由接口自述的 `hour` 反解**：`issue := forecastTime − hour`，即"接口自己声明的时效零点"。**`publishTime` 不可当锚点**——实测换产品循环时它前进 8h 而 `hour` 基准前进 12h，用它会令同一批有效时刻的 lead 整体偏移数小时，而 lead 正是天桶分组的唯一依据。降级阶梯（每步写入 `issue_source`/`issue_notes`）：少数点 `hour` 异常 → 取多数基准；并列或产生负 lead → 退回 `publishTime`；再不可用 → 退回序列首点。
- **视野约 7 天**（最大 lead 153~165h，随产品循环而变），覆盖天桶 1..7。视野由产品循环决定而非抓取时刻：同一循环内响应稳定，`(站 × 模型 × 起报)` 幂等键与其发布节奏天然对齐，跳过重复抓取不损失样本。
- 与 `cma_ndfs` 同属中国气象局体系，但是**不同产品线与发布通道**：实测同刻温度 \|ΔT\| 中位 0.67~1.10℃、窗口总量比 0.53~0.80。横向比较时应视为"相关但独立"的两个源。

**中科天机 / 伏羲中期 / 风乌**：非官方网页接口，游客态可用但无官方契约，页面改版即可能失效（失败只影响该源，不阻断其他源）。

**eia-data 观测源（主源）**：页面结构改版会影响解析（已做双路回退），届时需调整 `obs/eia_data.py`。页面数据停摆（抓取成功但最新观测滞后 >3h）会以 WARNING 告警；该告警同时构成**降级触发条件**（见下一条），不再只是一行日志。报告"覆盖率"区同步展示全站最新观测时刻供读者核对。

**中国气象数据网观测源（`cma_data`，备用源）**：抓的是站点页 [data.cma.cn/dataGis/static/gridgis](https://data.cma.cn/dataGis/static/gridgis/#/pcindex) 前端调用的接口

```
GET /app/Rest/liveDataService/station/{WMO站号}/latest?datetime=<YYYYMMDDHHMMSS>
```

无官方契约（前端 bundle 逆向而来），但**游客态可用、无需凭据**，寻址用的正是配置里已为 `cma_public` 配好的 `cma_id`。契约细节（全部经逐点实测，见 `obs/cma_data.py` docstring）：

- ⚠️ **`datetime` 参数按 UTC 解释，返回的 `D_datetime` 是北京时。** 把请求时刻直接当北京时传进去，会静默拿到 **+8 小时**的观测——不报错、不告警，只是每小时都对错对象。证据（站号 59265，2026-09-19）：请求 `00:00` 返回 `08:00`、请求 `14:00` 返回 `22:00`，前 15 行严格满足 `回显 = 请求 + 8h`，其后封顶于"当前最新可得时刻"。故实现：请求 = 目标北京时 − 8h；**时间键一律取响应自述的 `D_datetime`**；回显晚于请求计入告警（语义漂移），回显早于请求属正常封顶。
- **要素码**（与 eia-data 存档逐点对拍确认）：`V12001` 气温、`V13003` 相对湿度、`V10004` 气压、`V11293` 风速、`V13019` 前 1 小时降水、`V20001` 能见度。对拍范围覆盖 4 站 12 个连续整点与 8 个降水事件：气温 `|ΔT| = 0.00℃`、降水 `|ΔR| = 0.00mm`（含万宁 2026-09-19 13:00 的 8.8mm 这类强降水）。
- **一次只返回一个时刻**，故按窗口内每个整点各请求一次；本地已有的时刻不重复请求（复核窗口内最近 6 小时例外）。实测 12 次连发约 5.3s，无限流迹象。
- **失效形态是 `HTTP 200 + content: {}`**（站号写错、时刻超范围、参数非法都如此）。按"空 content = 该时刻无观测"处理：单点为空即缺测（**绝不折算 0.0**），整窗全空即抛错视为抓取失败。
- **UA 必须在白名单内**：实测空 UA → HTTP 403、`python-requests/2.31.0` → 服务端直接断连。UA 与 Referer 集中在 `obs/cma_data.py` 的 `HEADERS` 单点定义，被误伤时只改这一处。
- **它不是独立观测源，而是同一批 CMA 观测的另一个出口**（两边逐点完全相等即是证据）。价值在"eia-data 改版时观测不断供"，**不在交叉验证**——真要交叉验证需要一个非 CMA 的观测来源。

**观测编排的降级判定（`obs/chain.py`）**：主源只要满足"未抛错 且 最新观测滞后 ≤ `obs_stale_hours`（默认 3h）且 覆盖小时数 ≥ `obs_min_hours`（默认 6）"就直接采用，**完全不请求备用源**。否则降级：被降级的源**已有的历史小时仍然参与合并**（所以"主源停摆 8 小时"的结果是"旧小时来自主源 + 新小时来自备用源"，而不是整段换源），备用源只补它缺的时刻。合并按优先级进行，**高优先级源已给出的时刻不被覆盖**——绝不做"谁后写谁赢"（那会让权威值取决于抓取顺序，不可复现）。每轮的 `ChainReport` 记录谁试过、谁顶上、补了多少位。

## 10. 结论能信到什么程度

- **样本期长度是第一约束**。样本期一两周时置信区间天然很宽，名次前后更多是抽样运气（带 † 的行尤其如此）。冠军横幅现在**直接写出这个事实**：样本天数、重采样块数、90% 区间中位宽、**与第一名区间有重叠的源有多少家**（这个数字通常远大于读者的直觉）。置信区间、冠军频率与权重敏感性是随报告一并给出的"结论可靠度"信息，解读时应结合。
- **三个"不同尺"的残余混杂**：
  - 时效长短 —— **已由难度对齐消掉**（总榜）；分时效榜则天然同尺。
  - 验证期长短 —— 新源只在自己入榜后被测。**已按"验证日数"列披露但未强制拉平**（那会为一家新源砍掉所有人的样本）。实测同一批源换到较短那段日子重算，分数变动最高 7.3 分。
  - 抓取频次 —— 已证伪：桶内平均 lead 各家一致。
- **降水分在干燥月份样本稀薄**：按天 1mm 阈值下若某维缺项，该桶不进总榜（两维齐备才算综合分），该行不入围冠军竞争。
- **总榜是加法假设**：源 × 时效的交互请看分时效榜与**技巧剖面**（短/中/长三段各自的名次）。交互项占多少方差现在有具体数字（报告"🔬 这份名次有多结实？"一节），读者可以自己判断"一个数字"够不够用。
- **"起报时刻"不是同一回事**：五种锚点语义各有各的可复核性，起报锚点≈抓取时刻的源，其声明时效会系统性长于实际时效。这类源在榜上带 **⚠️ 口径存疑** 标记，且**不被单独摘出来排另一张榜**——我们选择"如实标注 + 让读者知情"，而不是替读者做取舍。若你不接受这类口径，请直接用行内的 `起报锚点` 信息自行过滤。
- **本轮审查留下的、尚未解决的已知缺口**：
  - **观测源的单点依赖已解除，但没有真正的交叉验证**（2026-09 修正）。抓取侧现有两个源（eia-data 主源 + 中国气象数据网备用源）与自动降级，页面改版不再让评估停摆；但两者输出**逐点完全相等**，说明它们是同一批 CMA 观测的两个出口，因此**不构成独立验证**。"这条实况对不对"仍然只有一个信息源。要真正的交叉验证，需要接入一个**非 CMA** 的观测来源（例如 METAR 报、机场自观），这尚未做。
  - **数据体积已有分层治理，但 `.git` 历史需人工回收一次**（2026-09 修正）。工作区增长已封顶：`compact` 把已结束月份合并为月度 bundle（实测 21× 压缩、文件数降两个数量级），超过保留期（默认 13 个月）的冷层出仓，`footprint` 看门狗每轮盯体积。但**归档动作不会回收 `.git` 里已存在的旧版本**——删掉的文件仍留在历史里，这部分只能靠一次人工的 `git filter-repo` 重写历史（步骤见 [第 3 节](#数据体积怎么持续可控)）。未迁 git-lfs：`compact` 之后冷层约 40 MB/年，用 lfs 的复杂度不划算。
  - **报告仍是单文件**（约 1.5 MB，含内联 ECharts 与全部数据）。拆成 `report.json` + 精简 HTML 会更快、也便于对 JSON 做快照回归，但尚未动。
  - **CRPS / 概率评估轨道**尚未建立（提供集合产品的源目前只评确定性指标）。
  - **留一站交叉验证**尚未做（4 个站轮流 held-out 看名次稳定性）——它能直接回答"结论能不能外推到别的站点"。
  - **观测源健康度未进 `reports/health.html`**：降级信息目前只落在每轮日志（`ChainReport`），看板仍只覆盖预报源。把观测源的降级次数与补位小时数也画进看板，是下一步该做的事。
