# 天气预报 API 准确度评估系统

自动抓取多个来源的数值天气预报，与事后到达的实况观测对比，用 [`cyeva`](https://github.com/caiyunapp/cyeva) 评估**气温**与**降水**的准确度，生成可在线浏览的多模型对比排行榜（GitHub Pages 部署后即网站首页 `reports/index.html`）。

目前接入 10 个预报源、25 个模型（ECMWF/GFS/ICON/CMA/GRAPES 等国际主流模式，以及彩云、和风、中科天机、伏羲、风乌、中科星图、AccuWeather、MSN 等国内可用的商业与 AI 预报），覆盖 4 个广西/海南气象站。

## 核心设计：存档先行

预报检验的第一性原理：**预报必须在实况出现之前存档固定**，事后才与观测配对比对，否则任何"评估"都可能被事后取数污染。因此系统的工作方式是：

1. 每次定时运行，把当时能拿到的**起报快照**（起报时刻 + 逐小时序列）原样封存进 `data/`，永不修改；
2. 观测到达后，按时间戳把封存的预报与观测逐点配对；
3. 每个样本按其**实际时效**（lead = 有效时刻 − 起报时刻）归入对应的「提前 N 天」天桶，这是连续数值预报检验的标准做法；
4. 严格模式：不回填历史起报，数据从首次运行起逐日积累，样本随时间自然变厚。

## 快速开始

```bash
python3.12 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt -r requirements-dev.txt
pip install --no-deps cyeva==0.2.3   # 必须单独装，见下方"依赖说明"

export PYTHONPATH="$PWD/src"         # src 布局且未打包，需手动加导入路径

python -m weather_eval fetch-obs                                # 抓观测
python -m weather_eval fetch-forecast                           # 抓 Open-Meteo 快照
python -m weather_eval fetch-forecast --source tianji           # 其他源同理，凭据先设环境变量
python -m weather_eval report                                   # 生成 reports/index.html
```

抓取是幂等的（按 站点×模型×起报时刻 去重），重复运行不产生冗余数据；单次失败不丢数据，下次运行会自动补回近 24h 的观测窗口。

### 命令一览

| 命令 | 作用 |
|------|------|
| `fetch-obs` | 抓取各站近 24h 观测并归档 |
| `fetch-forecast [--source X]` | 抓取预报起报快照并归档（源见上表，默认 Open-Meteo） |
| `report` | 用"本月 1 号至今"的累计数据覆盖更新主报告 `reports/index.html` |
| `monthly [--month YYYY-MM] [--force]` | 把某月冻结为月度归档 `reports/monthly/YYYY-MM.html`（默认上一自然月）；已存在的归档拒绝重写，`--force` 才允许重建，随后重建主报告 |
| `archive [--days 60] [--apply]` | 把 issue 早于保留窗口的旧快照 gzip 归档（`.json` → `.json.gz`，压缩比约 8~12×）；默认 dry-run 只列候选，`--apply` 才执行。评估读取侧对两种扩展名一视同仁，归档不改变任何指标口径。建议每月手动跑一次（或挂 cron），避免起报快照（实测约 139 份/天）把仓库撑爆 |
| `all` | `fetch-obs` + `fetch-forecast` + `report`，GitHub Action 的主步骤 |

### 依赖说明（重要）

- Python 须为 **3.12**（cyeva 0.2.3 不支持 3.13）。
- cyeva 的元数据把 `pint` 误钉为 0.24.3，而 0.24.3 在 Python 3.12+ 上无法导入，故必须用 `--no-deps` 单独安装 cyeva，由 `requirements.txt` 提供可用的 `pint==0.24.4` 及其真实依赖（pandas/scipy）。升级 pint 版本前先确认 cyeva 仍可导入。

## 自动运行（GitHub Actions）

1. 推送仓库（需包含 `data/` 与 `reports/`），在 **Settings → Pages** 把部署源选为 **GitHub Actions**。
2. 工作流 `.github/workflows/eval.yml` 每天**北京时 06:00 / 13:00 / 20:00** 运行：抓观测和各源预报 → 覆盖更新主报告 → 提交数据 → 部署 Pages。提交与部署步骤带 `if: always()`——即使某一步抓取/报告失败，当轮已落盘的预报快照也会入库（预报快照错过起报即无法追补），失败信号由作业状态保留。每月 1 号（当天任一次运行，规避定时延迟）额外把上一自然月冻结为月度归档（也可 `workflow_dispatch` 手动指定月份；已存在的归档自动跳过，绝不重写）。
3. 各商业源的凭据配置为同名 Secret（`CAIYUN_TOKEN` 等）；**未配置的源自动跳过**，已配置但抓取失败只标注该步骤、不阻断主流程。

## 评估方法

- **配对**：预报与观测按北京时整点时间戳精确配对。观测 `rain@t` 覆盖 (t−1h, t]；各预报源的逐小时降水入库口径见下表（假设与换算均在各 provider docstring 中留档，并随积累的数据定期标定复核）：

  | 源 | 入库口径 | 说明 |
  |---|---|---|
  | Open-Meteo / 彩云 / 和风 / 中科星图 | 源原生序列直接透传 | 按"前 1 小时累计"同标注配对；彩云/和风的窗口方向官方未逐字明示，已做 −1/0/+1h 平移标定（2026-08-30，首月样本）：无 1h 错位证据，彩云 POD 偏低在任何平移下都存在，判为预报技巧差异而非对齐问题 |
  | 中科天机 / 伏羲中期 | mm/h 降水率近似 | 源为速率量，作为"前 1 小时累计"的近似配对（docstring 已披露） |
  | 伏羲确定性（FuXi-Det） | 逐时刻累计直接透传 | 累计窗口官方未明示，按"前 1 小时累计"同标注配对；带单调性哨兵——若序列呈"自起报累计"形态即告警，绝不静默入库 |
  | 风乌 | 6h 累计均摊 | tp6h 非重叠平铺窗口均摊 /6，总量严格守恒；滑动 6h 窗口差分在数学上不可恢复 1h 分辨率（docstring 已论证） |
  | MSN 天气（中国天气网） | `rainAmount` 直接透传 | 累计窗口方向未明示，按"前 1 小时累计"同标注配对；带强校验哨兵——`raAccu` 是按自然日重置的日内累计，"日内 raAccu 增量 == 当小时 rainAmount"不一致即告警（同时反证 rainAmount 为逐小时量而非自起报累计）。❌ 严禁使用 `precipitation` 字段：它是降水概率百分数，却带 `precipitationHeightUnit: "毫米"` 的误导性单位标注 |
  | AccuWeather | 整体移位 1h | TotalLiquid@t 推断为 (t, t+1h]，入库前移为 (t−1h, t] 标注；2026-08-30 复核标定：证据不足（p≈0.06 且事件级矛盾），假设保留、待满月样本后复标 |

  各源口径偏移如需调整，应在对应 provider 内实现并留档（`config/stations.yaml` 不再提供全局偏移配置——它是按源而非按站生效的）。
- **样本与时效**：每个（起报, 有效时刻）组合是一条独立样本，按实际时效归入 1–16 的「提前 N 天」天桶；短时效样本天然更多，时效曲线正是要反映"越临近越准"。另做按天评估（北京时自然日的日最高/最低气温、日降水量；观测与预报任一侧当日非缺测小时数不足 `daily_min_hours`（默认 20）时该天不入样，缺测绝不折算成 0.0）与 1–72h 逐小时曲线。

### 逐日预报补位（按天轨道，`daily_source_fallback`，默认开）

多数 API 的**逐日预报比逐小时预报覆盖得更远**（逐小时常止于 5–10 天，逐日可到 15 天）。逐小时一断供，按天评估就跟着断在第一段时效上——即便该源明明还有日预报。为此快照支持一个可选的**逐日预报块**（契约见 `forecast/base.py`）：

```json
"daily_time": ["2026-09-06", "2026-09-07"],
"daily": { "模型名": {"temp_max": [...], "temp_min": [...], "precipitation": [...]} }
```

评估时按天轨道走**双轨**：该日逐小时覆盖达标 → 用逐小时聚合（与历史存档同一口径，旧数字不变）；覆盖不足或没有逐小时数据 → 回退源自带的日产品值，该条样本按 `temp_src`/`rain_src` 记 `"daily"` 并与 `"hourly"` 分开计数，报告"明细表②"以「日产品补位」列按"补位数/总数"披露。三条边界（第一性原理，不可越界）：

1. **绝不由日产品反推逐小时序列**——插值/均摊是凭空造出日内变化；逐小时指标、分时效榜与总榜永不掺入日预报的样本。
2. **观测侧覆盖门槛不放松**：实况当天不足 `daily_min_hours` 照样不入样；日产品缺测就是缺测，绝不折算 0.0。
3. **口径差异只披露不消除**：日产品的日界窗口与"逐小时求和"相差约 1 小时边界；同一日偏移桶内可能两种来源混存（不同源、甚至同源的不同天），横向解读以补位列与分时效榜为准。日产品的日界必须是北京时自然日——中国天气网"白天/夜间"那类日界不能照抄，接入前必须在 provider docstring 里核实留档。

日产品**抓取失败不拖垮整份起报快照**（逐小时是主干，错过起报无法追补），缺失块以 WARNING 暴露、评估自动回退纯逐小时口径；`daily_source_fallback: false` 可整体关回旧口径。各源接入状态（2026-09-05 逐源实测核实，证据与口径假设见各 provider docstring）：

| 源 | 逐日块 | 说明 |
|---|---|---|
| Open-Meteo | ✅ 全三要素 | 参考实现：同一次请求顺带取回，零额外调用。该源逐小时本就覆盖满 16 天，补位保持休眠 |
| 和风天气 | ✅ 全三要素 | 旧版 v7 逐日 3/7/10/15/30d 逐档回退（precip 为官方整日降水量）。逐小时止于 240h=10 天，逐日可到 30d——**真实时效增益 +5~20 天**。v7 官方 2027-02-01 停服，届时自动退化为不带块；新版 v1 daily 仅 10 天且无整日降水量字段，不接 |
| AccuWeather | ✅ 全三要素 | 官方逐日 15/10/5/1day 逐档回退；降水 = Day/Night 两个半日 TotalLiquid 之和（details=true）。逐小时 10 天 → 逐日 15 天（订阅开放 15day 时）。半日窗口（约当地 06/18 时）与自然日的边界差已留档 |
| 中科星图 | ✅ 仅温度 | `day/area` 15 天：tem_max/min 与自家逐小时对拍一致（±1°C）。**降水拒绝接入**——实测 pre_day/pre_night 呈恒 5.0 的量级码形态且与自家逐小时矛盾 90 倍，逐小时 5 天 → 逐日温度 15 天 |
| 彩云天气 | ✅ 仅温度 | 同请求把 dailysteps 提到 15（官方上限）：daily.temperature[].max/min 即全天最高/最低。**降水拒绝接入**——daily.precipitation 只有日内统计量（max/min/avg/probability），无累计字段。逐小时本就覆盖 16 天，接入价值在逐小时被 Token/UA 截断时 |
| 中科天机 | ❌ | 单点接口无逐日产品：5 个模式 × 6 个逐日要素候选码全部实测为空（docstring 留档） |
| 风乌 | ❌ | 官方变量表仅 16 个逐小时要素，前端 API 面无逐日端点 |
| 伏羲（中期/确定性） | ❌ | 两条产品线的变量表均无逐日极值；次季节线的 t_min/t_max 属不同产品线（分位值、非自然日），不混用 |
| MSN 天气 | ❌ | SSR 的 daily 汇总两次实测与任何可识别日界（自然日/白天-夜间窗口）都对不上（差 1~2°C、方向不定），疑占位值——与观测日界无法对齐的极值入库等于注入系统噪声（docstring 留档证据） |

- **样本下限**：所有指标附样本数 n；`n < 5`（`min_sample`）视为"样本不足"，不出结论。
- **有效样本量 n_eff**（统计推断层，2026-09-06）：逐小时误差强自相关（lag-1 ρ 实测 0.64~0.91），名义 n 会把同一信息重复计数（实测高估 4.6~20.5 倍）。`min_sample` 判定与总榜入围门槛均以 n_eff = n·(1−ρ₁)/(1+ρ₁) 为准（实现见 `stats.py`，按站独立估计、同一有效时刻只取最新一版起报）。
- **相关系数与回归斜率按站内合并**：跨站池化的 r 混入"复现站间气候差异"这一容易得多的任务（实测与站内口径差最多 0.084，约合 1.3 个综合分）。r 在各站内部计算后按 Fisher-z 变换加权合并，斜率按样本量加权合并；池化值保留在 `r_pooled`/`slope_pooled` 并列披露。
- **指标**：温度 9 项（RMSE/MAE/MBE/±1°C·±2°C 准确率/相关系数/回归斜率/RSS/χ²），降水 11 项（晴雨二分类 8 项：准确率/POD/FAR/POFD/漏报率/TS/ETS/BIAS ＋ 雨量连续量 3 项），另有逐小时雨强 5 档与 24h 累计 6 档的分级指标。全量定义见 `evaluate.py` 模块 docstring。

### 评分体系（排行榜）

综合得分 =（温度分 + 降水分）/ 2，每个子分由互不重复维度的代表性指标加权而成，统一换算到 0~100；某指标缺数据时按剩余权重归一（不因缺项扣分，缺失维度在榜单以 — 明示）。

- **温度分**：±2°C 准确率 25% ＋ RMSE 换算分 25% ＋ 相关系数 r 15% ＋ ±1°C 准确率 10% ＋ MAE 换算分 10% ＋ |MBE| 偏差换算分 10% ＋ 回归斜率换算分 5%。
- **降水分**（2026-09-06 重构）：**主评估轨道为按天 24h 累计、日雨量 ≥1mm 记"有效降水日"**（`rain_daily_threshold_mm`，业务惯用口径）。ETS 35%（首位）＋ TS 25% ＋ POD 15% ＋ 100−FAR 15% ＋ |BIAS−1| 换算分 10%。
  - **为什么换轨道**：逐小时 ≥0.1mm 口径下数值模式普遍每小时产生微量降水（drizzle bias），实测各源超报 2.7~15.3 倍、全模式 ETS ≤0.054（满分 1.0）、降水分被压在无区分度的窄带里；24h 累计让毛毛雨在求和中自然抵消，1mm/日阈值下 ETS 上限恢复到 0.25（阈值扫描 0.1/0.5/1/2/5/10mm，见 `scripts/calibrate_daily_threshold.py`，可复现）。
  - **为什么晴雨准确率 acc 不入分**：它主要由气候基率决定（无雨日 70%+，"全答无雨"即可拿高分），不是技巧；ETS 本身已做过基率校正。旧权重下 POD 高于 FAR+BIAS 之和，甚至奖励"超报占便宜"（超报 15 倍的源反而高于克制源）——现 POD 15% 低于 FAR+BIAS 25%。
  - 逐小时晴雨指标保留为**诊断视图**（明细表），不进综合分。

权重表在 `evaluate.py` 的 `TEMP_SCORE_PARTS` / `PRECIP_SCORE_PARTS`，是评分、页面"评分构成"表与本文件三处的单一数据源。RSS、χ²、雨量 RMSE/MAE/MBE 等指标计算但不入分（理由见代码注释与页面说明）。

### 排行榜的两层结构（总榜 + 分时效榜）

预报难度随时效单调上升，横向比较的前提是"同一难度"，因此榜单分两层：

- **分时效榜**（「提前 N 天」）：按时效分天桶，每桶一张榜。同桶内各家比的是同一难度的预报，这是公平基准。桶内温度分来自逐小时轨道，降水分来自按天累计轨道。
- **总榜**（`leaderboards["all"]`）：各天桶综合分的**等权平均（macro-average）**，回答"综合所有时效谁最准"。每个源先在自己的每个可用时效各得一分、再跨时效平均——2026-09-06 前的"全部样本池化打分"口径会让时效构成直接改变结论（实测 25 源中 14 个在同难度对照下名次变动 ≥5），macro 化后这一混杂降级为"影响各源的可用桶数"。

总榜行附带的公平性与不确定性信息（2026-09-06 新增）：

- **覆盖时效**：按各指标**实际参与计算的样本**（两侧同时有值）分"温度/降水"两轨统计的最长覆盖天数——序列尾部的 null 段既不入样也不计入覆盖。
- **90% 置信区间与显著性**：按天分块 bootstrap（块长 1 天，`bootstrap_runs` 默认 500 次，固定种子可复现）给出综合分区间；名字带 † 表示与第一名的差距在 90% 置信下与 0 分不开。块重采样同时化解了逐小时自相关问题。
- **冠军频率与权重敏感性**：把 12 项权重各扰动 ±40% 重复 500 次（`sensitivity_runs`），报告展示冠军在入围源之间的分布——多家轮换说明头名之争并未"一锤定音"。
- **入围门槛（qualified）**：n_eff ≥ `min_board_neff`（默认 30）**且**温度/降水两个维度都有分。未达标源列"样本积累中"、不参与冠军竞争——名义样本只有 156 条、覆盖 1 天、甚至连降水维度都没有的源，不该凭单一温度分坐上"综合冠军"。首页冠军横幅只读达标源（总榜无人达标时回退分时效榜中两维度齐备的第一行）。

跨覆盖范围的同难度精确对比以分时效榜为准。

## 报告

- **主报告 `reports/index.html`**：展示"本月至今"的累计评估，每次运行覆盖更新（数据本体在 `data/` 持续积累，报告只是当前数据的一个视图，不堆文件）。页面按"榜单优先"组织：冠军结论（全时效总榜第一）→ 表格式排行榜（默认总榜，可切每个「提前 N 天」分榜，可排序、搜索，总榜附「覆盖时效」列）→ 得分随时效衰减趋势 → 气温/降水对比图 → 实况对比/热力图/分站图 → 进阶区（按天评估、分级降水、全指标明细表）→ 名词词典。
- **月度归档 `reports/monthly/YYYY-MM.html`**：每月 1 号把上月冻结，永不改动；归档后立即重建主报告使归档出现在首页。
- 每月 1 号主报告切换到新月份窗口后，页面短暂回到"样本积累中"属正常现象，上月完整结果在归档里。

## 扩展

- **新增站点**：在 `config/stations.yaml` 的 `stations` 下加一项（`id`/`name`/`lat`/`lon`/`obs_url`，`obs_url` 为 eia-data 该站"气象站基本信息"页的 URL）。
- **新增模型**：Open-Meteo 模型直接加入 `models` 列表；中科天机模型需先在 `forecast/tianji.py` 的 `MODEL_SPECS` 登记映射。
- **新增预报源**：实现 `forecast/base.py` 的 `ForecastProvider` 接口（返回统一结构的起报快照，支持共享时间轴的 dict 或各模型独立快照的 list 两种形态），在 `__main__.py` 的 `SOURCE_SPECS` 登记一个 `--source` 值（模型集合与提供方工厂在同一处登记，勿分两张表），评估逻辑无需改动。**报告层三张登记表必须同步**：`report/render.py` 的 `MODEL_LABELS`（中文名）/ `MODEL_COLORS`（配色）/ `MODEL_FAMILIES`（源分组）——该契约由守卫测试 `test_all_models_registered_in_report_layer` 机器校验，漏登任何一张表 CI 直接红（MSN 曾因此以原始 id 显示在总榜第 3 名附近）。HTTP 重试/熔断直接用 `forecast/http.py` 的 `request_with_retries`（4xx 立即熔断、5xx/429/网络错误退避重试、末次不 sleep），不要再手写循环。现有 `caiyun.py`/`qweather.py`/`geovis.py`/`accuweather.py`/`msn.py` 可作参考，覆盖了官方 API、网页接口抓取、档位回退、SSR 状态抽取等常见形态。
- **逐小时覆盖短于逐日的源**：按 `forecast/base.py` 的契约把该源的逐日预报一并封存进快照的 `daily_time`/`daily` 块（日产品抓取失败降级为不带块的快照），按天评估即可自动越过逐小时断供点——参考 `open_meteo.py` 的 `_parse_daily`、`qweather.py` 的 `_fetch_daily_block`（档位梯子型）、`accuweather.py` 的 `_fetch_daily_block`（半日分量求和型）、`geovis.py` 的 `_fetch_daily_block`（仅温度型）；日界与字段口径假设必须先实测核实并写进该 provider 的 docstring，源的逐日产品若只有概率/量级码/日内统计量（无定量累计），对应要素一律置全 null 并留档拒绝理由（见 base.py 契约）。

## 已知约束

- **评分的统计边界**：榜单结论的可信度受样本期长度制约——样本期一两周时置信区间天然很宽，名次前后更多是抽样运气（名字带 † 的行尤其如此）；阈值 1mm/日的按天降水分在极干燥月份样本稀薄，降水分缺项时综合分退化为温度分口径（该行不入围冠军竞争）。置信区间、冠军频率与权重敏感性是随报告一并给出的"结论可靠度"信息，解读时应结合。
- **非官方网页接口源**（中科天机、伏羲中期、风乌）：抓取的是其可视化页面背后的接口，游客态可用但无官方契约，页面改版即可能失效（失败只影响该源，不阻断其他源）。
- **彩云天气**：返回点数与 User-Agent 强相关，代码中固定的 UA 勿改（改了会被静默截断至约 48 小时）；逐小时时间戳锚定在请求时刻，已下取整到整点配对。
- **AccuWeather**：其服务条款限制将数据用于"评级、排名、评审"类用途，与本项目公开排行榜的定位存在潜在冲突，是否接入请自行评估。定位是"最近城市吸附"而非格点，样本代表最近城市——公开报告的排行榜区会以"口径注记"展示其实际吸附距离；逐小时降水的入库移位是一项已留档、待满月样本复标的推断假设（见"评估方法"口径表）。
- **MSN 天气（msn.cn，底层中国天气网）**：抓取的是其天气预报页**服务端渲染内嵌的状态块**（`redux-data`），无独立 JSON 契约，页面改版即可能失效（失败只影响该源，不阻断其他源）。其余约束：
  - **一次只渲染一天逐小时**，一份快照需按 `day=1..10` 抓 10 次请求/站（4 站 ≈ 40 次/轮，是本仓库请求量最大的源）；`day>10` 会被服务端静默回退为滚动窗口，不可用于延长时效。
  - **起报时刻是推断值**：接口不回显模式起报轮次，以响应的 `lastUpdated`（数据更新时间）下取整整点作为起报锚点——语义同彩云的"请求时刻锚定"。实测 `lastUpdated` 约每 10 分钟推进，故每小时内的重复抓取会被幂等键合并为一份快照。
  - **时效上限约 9.3 天**（225 个整点，最大 lead 224h → 覆盖天桶 1..10），短于配置的 16 天：总榜"覆盖时效"列会显示 10d，跨源比较时需计入该差异（README"总榜"一节已披露的原理性混杂）。
  - **温度为整数摄氏度**（实测恒为整数，如 30/29/28），而观测有 1 位小数：该源自带约 ±0.5°C 的量化误差，RMSE/±1°C 准确率等指标相对其他源（如彩云的小数温度）存在系统性劣势，横向比较时应知情——这是数据源本身的精度上限，非接入缺陷。
  - **最近城市吸附**（同 AccuWeather 语义）：请求坐标被吸附到中国天气网的城市站点，实测 4 站吸附距离 1.8–7.0 km，报告"口径注记"会展示（各站吸附到的城市名会一并列出）。
  - **抓取途中数据滚动更新**：10 次请求跨越数秒，若期间 `lastUpdated` 推进（概率低），该轮分片会跨两个数据版本——实现以"一份快照绝不跨版本"为不变量：舍弃旧版本整体重抓（限 1 次），再漂移则中止并保残缺快照，绝不静默混合。
- **Open-Meteo 起报锚点**：Open-Meteo 不回显底层模式的真实起报轮次，快照锚点是北京时"当日 00:00"（与真实 init 相差 −8~+12h 且随抓取时刻漂移），且每天仅 1 份快照（后续抓取被幂等跳过）——同一「提前 N 天」桶内其预报难度与样本新鲜度和其他源（锚定真实轮次/抓取时刻、逐时封存）略有差异，跨源比较分时效榜时应把该差异计入（公开报告"口径与已知差异"区已披露）。
- **eia-data 观测源**：页面结构改版会影响解析（已做双路回退），届时需调整 `obs/eia_data.py`。页面数据停摆（抓取成功但最新观测滞后 >3h）会以 WARNING 告警，报告"覆盖率"区同步展示全站最新观测时刻（`coverage.last_obs`）供读者核对。
- **数据归档**：起报快照约 139 份/天全量进 git，长期会把仓库撑爆——定期跑 `python -m weather_eval archive --days 60 --apply` 把旧快照 gzip（评估读取侧自动识别 `.json.gz`，口径不变）。
- **Open-Meteo 免费档**约 1 万次/天、无需 Key，但批量回溯请控制频率。
